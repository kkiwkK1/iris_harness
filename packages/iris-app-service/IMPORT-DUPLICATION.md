# 导入侧的重复:一份表存两遍,以及那第二份到底买到了什么

**这是设计输入,不是实现。** 按派单:先量清**谁在读哪一份**,再定单源+投影还是两份并存。
量完之后结论和立项时的假设**不一样**,所以先说结论。

## 口径

- 语料:`E:\sillyTavern` 全部 **31 个 chat 文件 / 2454 行**,经产品自己的
  `parseChatFile` → `importChat` → `hydrateVariables` → `toFile` 走一遍。
- 只记形状与字节,不记内容。
- 所有数为本机单次测量,**未经第二人复核**。

---

## 一、重复是真的

一条 assistant 行的 `variables`,在导入之后同时存在于两个地方:

| 事件 | 谁写 | 谁读 |
| --- | --- | --- |
| `iris/st-meta` | `rememberFields`,把**所有非建模键**原样收起(`sillytavern.ts:110`) | 只有 `fieldsFor`,只在导出时(`:166`) |
| `iris/variables` | `hydrateVariables`,按候选位置挂 | `floorVariables` / 快照 / `prune()` / 卡的读路径 |

`MODELLED_KEYS` 是 `{name, is_user, mes, swipes, swipe_id}`(`sillytavern.ts:63`)——
**`variables` 不在其中**,所以它整份搭 `st-meta` 的车过去。

全语料测得:

```
st-meta 合计            27.58 MiB
  其中 `variables`      25.81 MiB  (93.6%)
```

**`st-meta` 有 93.6% 的体积是这一个键的副本。**

## 二、但它不是死重——我先这么以为,被自己的实验推翻了

`toFile()` 的顺序是:`exportMessages` 先按 `st-meta` 把 `variables` 原样放回,**然后**
用实时快照覆盖每一条 assistant 行。所以我的推断是:assistant 行的那份副本写了又被盖掉,
纯属死重,可以直接不存。

**做了才知道不对。** 把 assistant 行的 `variables` 在导入前删掉(于是 `st-meta` 不再
收它),再用原始行照常 `hydrateVariables`,导出与基线逐字节比:

```
31 个 chat:逐字节相同 1,不同 30
```

第一个不同的字节位置正好是 `variables` 原来所在处:基线里它在**原位**,去掉之后
`line['variables'] = …` 这一次赋值把它**追加到了对象末尾**,排在
`variables_initialized`、`is_ejs_processed` 之后。

再把两侧按键名排序后比内容:

```
2454 行:忽略键序后内容相同 2454,内容真的不同 0
        键序发生变化的行     1233   ← 恰好是全部 assistant 行
```

> **`st-meta` 里那份 `variables` 副本,买到的东西**有且只有一件:**它在行内的键位置**。
> 内容一字不差地由 `iris/variables` 那一份负责。

这条正是派单点名的那个不变式(972/972 逐字节往返)的实际形态:**往返的逐字节相等,依赖
的是键序,而键序目前是被一份 25.81 MiB 的完整副本"顺便"保住的。**

## 三、于是三个选项,和它们各自的代价

### 选项 A:保持现状

两份并存,`prune()` 只清 `iris/variables` 那一份——所以**长局清理对 93.6% 的体积不起
作用**。这是它今天最难看的一面:用户以为清理了,`st-meta` 那份原封不动。

- 代价:导入一份上游长局,我们的开销约为上游的 1.68 倍。
- 好处:零风险,往返不变式自动成立。

### 选项 B:`st-meta` 不再收 `variables`

- 省:**15.82 MiB**(语料全量,assistant 行)。
- 代价:**往返不再逐字节相等**——1233 行的 `variables` 会跑到行尾。内容不丢,顺序变。
- 这个代价大小取决于一件我**没有量**的事:**上游或第三方工具是否有任何东西依赖键序**。
  JSON 对象键序在语义上无意义,但"我们的导出和原文件逐字节一致"是一条我们自己立过的、
  可验证的强保证,放弃它就等于放弃一种非常廉价的回归检测手段。

### 选项 C:只存位置,不存值(**已裁 2026-09-03,采纳**)

`st-meta` 不收 `variables` 的**值**,改为记住该行的**键序**(一个键名数组),导出时按它
重排。

```
存值(今天)   15.82 MiB
只存键序       0.20 MiB      单行最大 181 B
                            ── 80 倍
```

- 省:**15.62 MiB**,同时**往返逐字节相等继续成立**。
- 代价:`exportMessages` 多一步"按记录的键序重排",而且这一步要能容忍
  **新增键**(记录里没有的键排在末尾)与**消失的键**(跳过)。
- 附带的好处:键序从"某份副本的副作用"变成**一件被显式记录的事**。今天如果有人改动
  `toFile` 的赋值顺序,往返就会悄悄坏掉,而没有任何注释说明为什么不能改。

### 裁定的理由,以及它为什么不是「省字节」

未查第一条(有没有别的消费者依赖键序)已答一半:**上游 SillyTavern 读 JSON 不看键序**。
所以逐字节往返**不是上游要求的兼容性,是我们自己立的保真度主张**。

这不削弱 C,反而正是选 C 而不选 B 的**全部**理由:

- **B 保住内容,丢掉主张**——省下同样的体积,代价是放弃一条我们自己能验证的强保证。
- **C 两个都保住,而且更便宜**(0.20 MiB 对 15.82 MiB)。

换句话说,这里要权衡的从来不是"字节 vs 风险",而是"**一条可验证的主张值不值 0.20 MiB**"。
写成这样是因为下一个读到这里的人会想问"既然上游不看键序,为什么还要费这个事" ——
答案是保真度主张的价值不来自上游要不要,而来自**它是一种极廉价的回归检测**:导出与原文
逐字节相等这一条,能在没有任何专门测试的情况下抓住一整类改动事故。

## 四、和 §8 的关系

`DEVIATIONS.md §8` 管的是**清理之后怎么读**;这一份管的是**为什么一份表要存两遍**。
两件事在 `prune()` 上碰头:清理今天只覆盖 `iris/variables`。

**如果走 C,`prune()` 的覆盖面问题自动消失**——`st-meta` 里不再有可清理的变量体积,
剩下的都是真正无法从别处重建的字段。**如果保持 A,那就得让 `prune()` 也去改写
`st-meta`**,而那意味着清理要动"原样穿过的载体",风险高得多:那份载体的全部价值就在于
它是逐字原样的。
