# 快照怎么过边界:三个候选并排

**设计输入,不是实现。** 接 `FLOOR-ADDRESSED-VARIABLES.md` §七量出的那件事:
**结构化克隆的代价跟对象个数走,不跟字节走**。变量表占字节 45%、占克隆时间约 91%,
因为 `mes` 是几个大字符串而表是成千上万个小对象。

## 口径

最长那局(677 行 / 18.32 MiB `chat` 数组),中位数 5 次,Node 24。
**浏览器的 `postMessage` 用的是同一套结构化克隆语义,但常数未在浏览器里复核**——
相对关系应当成立,绝对毫秒不要当作前端实测。单人单次。

---

## 一、先把 224 ms 拆开:它不全是变量表

```
exportMessages 单独        124.3 ms
toFile(export + 挂表)      205.0 ms
   → 挂表那一步              80.6 ms
```

**三个候选没有一个能碰到那 124.3 ms。** 它是从日志重建 677 个行对象本身的代价,
和变量无关。**所以本文能省的上限是 80.6 + 87.7 = 168 ms,不是 309 ms**——
把这条写在最前面,免得三个候选被拿去和一个它们够不着的分母比。

## 二、候选一:变量表以 JSON 文本携带

每行的 `variables` 在快照里是**字符串**而不是对象树;frame 在 `getVariables({message_id})`
问到那一楼时同步 `JSON.parse` 并缓存。

```
宿主 stringify              22.5 ms
克隆(表为文本)             16.8 ms
克隆(表为对象树,今天)      87.7 ms
                          ─────────
宿主侧合计                  39.3 ms   对  87.7 ms      省 ~48 ms

frame 首次 parse:最大一楼    0.83 ms   (282.8 KiB)
frame 首次 parse:中位一楼    0.00 ms   (0.0 KiB — 多数楼被剥空)
```

**一个反直觉的地方值得单说:文本化之后 payload 变**大**了**——19.27 MiB 对 18.32 MiB
(转义的开销)——**而克隆时间掉到五分之一**。同一份数据,字节增加、时间下降。
这是 §七那条「时间和字节不成比例」的第二次出现,方向更极端:**如果按 payload 大小做
决策,会选错**。

**同步性保住**:`JSON.parse` 是同步的,而上游 `getVariables` 是同步的。按需解析,
最坏一楼 0.83 ms,中位数是 0——因为长局里多数楼已经被清理剥空,**「最坏」和「典型」
在这里差三个数量级**。

## 三、候选二:增量快照(每回合只发变化的楼)

```
带表的楼                    677 / 677
最新一楼                    281.1 KiB
它占全部表字节               3.3 %
```

理论上限很好看:一回合只有一楼的表变化,发 3.3% 即可。但代价不在字节上:

- **第一次快照仍然是全量**,省的是第二次之后。
- **frame 要跨回合持有状态**,而快照现在是无状态的:每回合重建一份完整事实。
  增量意味着 frame 手里那份的正确性取决于**每一次失效都没漏**。
- **漏一次失效的表现是「卡读到过期的表」**——不报错、表良构、值是上一回合的。
  这正是我们这几轮反复在修的那一族(静默、可信、错)。用一个**已知会静默出错的机制**
  去省一件候选一已经省掉的钱,不划算。

**不推荐**,除非将来快照大到候选一也扛不住;那时它的复杂度才值得。

## 四、候选三:和 WINDOWING 摘表同批

```
克隆(完全不带表)            7.6 ms
```

最便宜,但**它不是一个独立选项**:摘表之后楼层读失去依据,所以必须和「楼层读改走别的
路」同批落(`FLOOR-ADDRESSED-VARIABLES.md` §七那根绳)。而且摘表要先回答
「窗口带哪几楼」——而 §二已经证明「最近 N 楼」正好选中最肥的一段。

**所以它不是候选一的替代,是候选一之后的下一步。** 两者叠加时,候选一的 stringify
只作用在**仍然携带的那几楼**上,成本随窗口一起缩小。

## 五、推荐:候选一,而且它不必等 WINDOWING

| | 宿主省 | frame 代价 | 跨回合状态 | 依赖别的裁定 |
| --- | --- | --- | --- | --- |
| 一 文本携带 | ~48 ms | 按需 0.83 ms(最坏) | **无** | **无** |
| 二 增量 | 更多(第二次起) | 需缓存与失效 | **有** | 无 |
| 三 摘表 | ~80 ms | 需另一条读路径 | 无 | **WINDOWING + 楼层读同批** |

**候选一是唯一一个既不引入跨回合状态、又不依赖另一项裁定的**。它把今天最贵的一段
(克隆 87.7 ms)降到 16.8 ms,代价是宿主多花 22.5 ms 做 stringify 和 frame 按需
花不到 1 ms 做 parse。**净省约 48 ms/快照,而且它和候选三是叠加关系不是二选一。**

## 六、未查

1. **浏览器里的常数没复核**。相对关系(字符串比对象树便宜得多)是结构化克隆的性质,
   但 Node 与浏览器引擎的绝对值不同。**落地前应在真 frame 上量一次**,否则我们是拿
   Node 的数做前端决策。
2. **「能不能不 parse→stringify,直接从磁盘原文切出表的文本」——答案是不能**,而理由
   值得记:assistant 行的表**不来自磁盘**,来自实时日志(`#snapshotVariables()`),
   磁盘那份在导出时会被覆盖。要让它从头就是文本,得改的是**事件里怎么存表**,那是
   存储层的改动,不是传输层的。
3. **缓存失效**:候选一里 frame 缓存 parse 结果,快照每回合重建,所以缓存该跟着快照
   一起丢。**这一条不难但必须显式**——一个跨快照活下来的 parse 缓存,和候选二的
   过期表是同一个 bug。
4. 本文数字单人单次,未复核,且未在浏览器复核。
