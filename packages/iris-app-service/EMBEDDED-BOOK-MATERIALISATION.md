# 内嵌世界书的物化:把第二条装配通道换成一条记账

**这是方案,不是实现。** 裁定已下(2026-09-03):装配层对齐上游单通道,内嵌书物化到我们自己
的 `worlds/`,绑定关系记在我们的 store,**不写卡文件**。这份要回答的是「怎么做、什么时候
做、卡更新了怎么办、已经导进来的怎么办」。

## 口径

- 语料:`E:\sillyTavern` 的 19 张卡 + 我们 dev profile(`apps/iris/data/default-user`)的
  8 张,都经产品自己的 `CharacterLibrary` / `charWorldbookNames` 读。
- 本机单次测量,未经第二人复核。

---

## 一、为什么必须先物化再拆(这不是排序偏好,是数据)

上游装配层只读绑定名(`world-info.js:4363-4380` 的 `getCharacterLore`,`character_book`
一次都没出现);内嵌书只在用户点头后被 `importEmbeddedWorldInfo` 物化成具名书
(两个调用点 5594 / 6210 **都在 UI 点击流里,没有自动路径**)。所以上游那边**重复根本
不会产生**,而我们的「择一」规则是在给自己开的第二条通道打补丁。

问题在于我们现在**有多依赖那条通道**:

| | ST 安装 | **我们的 dev profile** |
| --- | --- | --- |
| 卡数 | 19 | 8 |
| `worlds/` 里的书 | 18 | **0** |
| 有内嵌书 | 17 | 7 |
| 绑定名能解析 | 16 | **0** |
| **今天真的走内嵌分支** | **2** | **7**(涉及 **407** 条) |

> **在我们这边,8 张卡里 7 张靠内嵌分支活着。** 先拆后补的中间态不是「少数卡退化」,
> 是**几乎每张卡开局变量全空**。

而 ST 那边只有 2 张走内嵌分支——因为它的 18 本书**是用户点头物化出来的**。
**那 18 本书就是我们要复现的终态。**

## 二、绑定名从哪来:大多数卡已经自带了

dev profile 里 7 个有绑定名的卡,绑定名指向:

```
ST 装了、我们没有   3   爱衣→爱衣妹妹v1.1、OVERLORD不死者之王→OVERLORD、Sgw→…
哪儿都没有          4   绿茵好莱坞→绿茵好莱坞、不要被神隐挑战-V1.5→不要被神隐挑战、…
```

看那四个「哪儿都没有」的名字:**卡自己的 `extensions.world` 已经写着它的内嵌书物化之后
应该叫什么**。那正是 ST 物化完的状态被记进了卡里,只是书文件没跟着卡一起旅行。

**所以铸名规则是:**

1. 卡的 `extensions.world` 有值 → **就用它**。这样我们物化出来的名字和 ST 物化出来的
   一致,同一张卡在两边指向同名的书。
2. 没有 → 用上游的铸名(`character_book.name` 或 `${卡名}'s Lorebook`,
   `world-info.js:5625`)。

**不要发明第三种命名。** 名字是卡和书之间唯一的链接,而 `WORLDBOOKS.md §3` 已经记过:
名字逐字使用,18 个真实书名里 13 个经 `toId` 会被改坏。

另外那 3 个「ST 有我们没有」的,暴露的是**另一个缺口**:**从 ST 安装导入一张卡时,它绑定
的书不会跟过来**。那不是本方案要解的,但它和本方案共用同一个症状(绑定名解析不了),
**必须一起报出来,否则物化会把本该是「书没带过来」的情况误当成「该物化内嵌书」**——
而这两者的正确处置相反:前者应该去取那本书,后者才该物化。

## 三、什么时候物化

**在导入路径上,不在装配路径上。** 装配路径必须保持「只读具名书」这一条,否则我们又
回到了两条通道。

- `character.import` 之后立即物化。
- **已经导进来的卡:一次性迁移**,在 store 首次读到「有内嵌书 + 无物化记录」时执行。
  上表说明迁移**不是可选的**——dev profile 里 7/8 张卡需要它。

## 四、卡更新了、内嵌书变了怎么办

这是裁定里点名要我写清的一条。

### 记什么

一张 `worldbook-bindings.json`(profile 层,和 `script-buttons.json` 同级),按
characterId 记:

```ts
interface MaterialisedBinding {
  /** 物化成了哪本书(就是绑定名)。 */
  name: string
  /** 物化时,卡内嵌书规范化后的哈希。用来判断「卡变了没有」。 */
  sourceHash: string
  /** 物化**写出去的那一刻**,书文件内容的哈希。用来判断「用户改过没有」。 */
  materialisedHash: string
  at: number
}
```

**两个哈希不是冗余,它们回答两个不同的问题**,而这正是「不能静默覆盖」能被判定的原因:

- `sourceHash` ≠ 卡当前内嵌书的哈希 → **卡更新了**。
- `materialisedHash` ≠ 书文件当前的哈希 → **用户改过那本书**。

### 四种组合,四种处置

| 卡变了 | 用户改过 | 处置 |
| --- | --- | --- |
| 否 | 否 | 什么都不做 |
| 否 | 是 | 什么都不做。**用户的书就是权威**,内嵌书只是种子 |
| 是 | 否 | **重物化**,静默。没有人的劳动会丢 |
| 是 | **是** | **不覆盖**,保留用户的书,**出一条报告** |

最后一格是全部的重点:**卡作者更新了世界书,而用户也改过同一本书**——两边都有正当主张,
自动合并会同时辜负两边。所以:保留用户的,**说出来**,把决定交还给人。

报告(`kind: 'script'`,借现有诊断总线):

> 卡「X」的内嵌世界书已更新,但你改过物化出来的书「Y」,所以没有覆盖它。

**为什么必须是一条报告而不是一次静默保留**:静默保留的症状是「我更新了卡,但新内容没
出现」,而**那和「更新失败了」长得一模一样**。这属于 `OBSERVABILITY.md` 的缄默族。

### 哈希算在什么上

`sourceHash` 算在**规范化之后**的内嵌书上(键序无关、`uid` 无关),否则卡作者重排一下
条目顺序就会被判成「内容变了」。`materialisedHash` 算在**书文件的字节**上,因为那一侧
要回答的是「这个文件还是不是我写出去的那个」——**字节相同就是没被动过,这是最强也最
便宜的判据**。

## 五、装配层要改什么

`resolveCardWorldbook` 的四段判定去掉第 4 段(内嵌书回退),其余三段(全局书叠加、
全局去重、绑定名读取)**一行都不用动**——它们本来就是对齐上游的。

两处成本,**都要逐个查而不是猜**:

1. **`source: 'embedded'` 这个枚举值有消费者**(契约/视图里出现过)。拆掉之后它要么
   保留但永不产生,要么改契约。**按「实现不是它的消费者」逐个查调用方。**
2. **`initVars` 走同一份 `entry.worldbook`**——`[InitVar]` 从书里读。所以物化和拆通道
   **必须同一批落**,中间态是「MVU 卡开局变量全空」。

## 六、和上游的差异,要记进 DEVIATIONS

| | 上游 | Iris |
| --- | --- | --- |
| 物化时机 | 用户点世界书按钮时 | **导入时,默认执行** |
| 绑定名写哪 | 写回卡文件的 `extensions.world` | **记在我们自己的绑定表** |
| 卡导回 ST | 已带 `extensions.world`,内嵌书已被剥离 | **卡原样,仍带内嵌书**,ST 那边照旧问用户 |

第二行是裁定的核心:**装配层仍是「单通道读具名书」,差别只在绑定名存哪**——那是存储层
的记账,不是第二条装配通道。第三行是它换来的好处:**我们不改用户的卡**。
