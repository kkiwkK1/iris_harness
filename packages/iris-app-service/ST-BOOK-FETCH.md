# 从 SillyTavern 安装取一本绑定书

**设计输入,不是实现。** 物化那批解决了「卡带着内嵌书来」;这份解决剩下的那半:
**卡指名的书在用户的 ST 安装里有,只是没跟着卡一起过来**。

## 口径与现状

本机实测(2026-09-03,materialise 落地之后):

```
ST 安装 worlds/            18 本   12.90 MiB   最大一本 2166 KiB
Iris dev worlds/            3 本   （全部是物化出来的种子）
dev 里解析不了的绑定名       4 个
   ST 安装里有的                2      ← 本方案的对象
   哪儿都没有的                 2      ← 已由内嵌书种子化,不是本方案的事
ST 的 globalSelect           1 本   在 ST 有,我们没有
```

**`globalSelect` 那个 1 我差点写成 0。** 第一次我读的是 `settings.json` 的
`world_info.globalSelect`,那个键**不存在**,`?? []` 把它变成了一个看起来正常的空数组。
真路径是 **`world_info_settings.world_info.globalSelect`**。同一个坑我在别处踩过一次并
记过档,这次是靠「零太干净了」才回头查的。**任何读 ST 设置的实现都必须用这条路径,而且
不能用 `?? []` 兜底一个缺失的键**——缺失和空选择是两件事。

## 一、安装在哪:用户配置的只读路径

- 一个显式设置(`IRIS_ST_DIR`,或设置项),**默认不配置**。没配置就是这个功能不存在,
  不去猜路径、不扫盘。
- **拒绝把它设成 `IRIS_DATA_DIR` 或其子目录**,启动时就拒,不是等出事:两者混在一起
  会让我们的写落到用户的真安装里,而本方案的全部前提是我们从不写那边。
- **只读,而且是文件级只读**:只读 `worlds/*.json` 和 `settings.json`。任何带
  确认/保存/发送/改状态语义的东西一律不碰。我们不调用 ST,也不假设它没在运行——
  **它可能正开着**,所以读到半个文件是正常情况:解析失败按「取不到」处理并报告,
  不抛、不重试到底。

## 二、什么时候取:绑定解析不了的那一刻,不做批量同步

**按需,不整库拷。** 整库拷 12.90 MiB 会把用户的书复制一份到我们这边,而两份从复制完的
那一秒起就开始各自漂移——这正是 `IMPORT-DUPLICATION` 那件事的形状。按需只取卡真正
要的:这台机器上是 **2 本,不是 18 本**。

触发点用**已有的那一个**:`bookFor`(导入路径与打开路径共用)。今天它在绑定名解析不了
时种子化内嵌书;加一步前置——

```
绑定名解析不了
  ├─ ST 安装里有同名书  → 取它(见三)
  └─ 没有              → 维持现状:内嵌书种子化(origin: 'seeded-from-embedded')
```

**顺序是「先找真书,再退种子」**,因为真书是用户的,种子只是卡自带的复制品。

## 三、取到之后:落到四格表的哪一格

绑定表已经记了 `materialisedHash`(写出去那一刻的字节)。所以「我们种下的那本,用户动
过没有」是已经能回答的问题,不需要新机制。

| 我们这边的状态 | 处置 |
| --- | --- |
| 没有这本书 | 直接写入,`origin: 'imported-from-st'` |
| 有,是我们种的,**用户没动过** | **替换**成 ST 那本,`origin` 改 `'imported-from-st'`,报告一句 |
| 有,是我们种的,**用户动过** | **不替换**,报告。两边都有正当主张,和卡更新那格同一个理由 |
| 有,不是我们种的(绑定表里没有 / 属于别的卡) | **不碰**,按撞名规则另铸名,报告 |

第二格是本方案的主线:**ST 那本是用户的书,内嵌副本只是种子**,所以真书一到就该顶上。
报告仍然要出——用户会看到条目内容变了,而「为什么变了」只有我们能说。

第三格值得单独说:**我们种下的书,用户可能已经在 Iris 里改过**。这时 ST 那本不是"更
权威",只是"另一个版本"。保留用户的、说出来,把选择交还给人——和卡更新那格是同一条
原则,所以不需要第二套判断。

## 四、取不到怎么报:三种"没有"要分开

一条 `kind: 'script'` 的报告,但**必须分辨是哪一种没有**,否则用户不知道该做什么:

1. **没配置 ST 路径** —— 「卡指名的书 X 没随卡导入;若你有 SillyTavern 安装,配置
   `IRIS_ST_DIR` 后重开这个聊天即可取用它」。**这是唯一一条要给行动指引的。**
2. **配置了,但那本书不在** —— 「在配置的 SillyTavern 安装里也没有 X」。用户可能配错了
   目录,或者那本书确实早就删了。
3. **配置了,书在,读不出来** —— 「X 存在但读取失败(可能 SillyTavern 正在写它)」。
   **这一条必须和第 2 条分开**:一个是"没有",一个是"有但这次没拿到",第二次打开可能
   就成功了,而合并成一句会让用户去找一本其实存在的书。

三种都**不阻塞**:取不到就走种子化,聊天照常开。

## 五、全局书能不能共用这套

**能,但触发点不同,而且要分成两件事。**

- **取书**:`globalSelect` 里的名字解析不了时,和绑定书走**完全一样**的四格表。同一个
  函数,只是调用者不同。
- **取选择**:「ST 选中了哪些书」是**另一件事**,而且是**用户的偏好不是卡的依赖**。
  我们的 `worldbooks.globalSelect` 是我们自己的设置(`WORLDBOOKS.md §2c`),
  **不该被 ST 的选择静默覆盖**——那是改用户在 Iris 里做过的决定。

  建议:**取书自动,取选择要用户点头**(一次性导入,不是持续同步)。持续同步意味着
  用户在 Iris 里改了选择、下次打开又被 ST 覆盖回去,而那是无法归因的。

本机曝光:**1 本**(ST 选中 1 本,我们没有)。数字小,但按「语料零是还没碰到、不是不
需要」的规矩,机制照上游建,不照这个 1 建。

## 六、未查

1. **ST 是否会在我们读的时候写**。我按"会"设计(读失败要能分辨),但没有实测过并发写
   下的表现。
2. **书名到文件名的映射**在 ST 侧是否就是"逐字 + `.json`"。我们这边 `fileFor` 有自己的
   安全规则,**两边对同一个名字可能落到不同文件名**,而本方案假设按名字就能在 ST 侧找到
   文件。18 本里有多少名字会在我们这边被改写,**没量**——这条会直接决定"ST 里有"这个
   判断准不准,**实现前必须补**。
3. **多 profile**:ST 安装可以有多个 user profile(`data/<user>/`),我们默认读
   `default-user`。多 profile 的用户怎么选,没设计。
4. 本文数字单人单次,未复核。
