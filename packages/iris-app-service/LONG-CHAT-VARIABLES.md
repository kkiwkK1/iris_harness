# 长局变量:上游的清理、我们的实际开销,以及两者不是同一个问题

Tier 1.3 的设计输入。三步照派单:量上游、量我们、提议。**结论先说:上游那套清理解决
的问题,在我们的存储里只占一半;另一半是我们自己造的,而且更大。**

## 口径

上游源码是本地检出 `.reference/MagVarUpdate/src/`(不是抓的 bundle)。我们这侧的数
来自语料里**最长的真实聊天**——`命定之诗与黄昏之歌v3.0.4/22 - ….jsonl`,18777 KiB,
**677 楼**——用本仓库自己的读路径(`parseChatFile` → `importChat` → `ChatStore.open`)
跑出来的,不是手写夹具。日期 2026-09-02。

---

## 一、上游做什么(逐字)

### 1.1 清理

`cleanup/cleanup_variables.ts`,`cleanupMessageVariables(start, end, interval)`:

- **删的是五个具名键**,不是整表:`initialized_lorebooks`、`stat_data`、
  `display_data`、`delta_data`、`schema`。别的键(卡自己塞的)留着。
- **逐 swipe 处理**:`_.range(0, swipes?.length ?? 1).map(...)`,缺的那层补 `{}`。
- `snapshot === true` 的层**整层保留**。
- 楼号是 `interval` 倍数的**保留并打标** `snapshot: true`。注释给了理由:用户把间隔
  从 50 改成 70,最小公倍数会让旧快照实质上变成 350 层一个——**打标是把当时的决定
  钉住,免得改配置追溯性地孤立掉已有快照**。
- 计数**按楼一次**,不按 swipe。
- **第 0 楼永不清理**(`legacy_chat.ts:94` 的注释:保证始终有快照能力)。
- 结束调 `saveChatDebounced()`。

### 1.2 什么时候跑

`cleanup/index.ts`,挂在 `MESSAGE_RECEIVED` 上,而且:

- **用户开关**:`自动清理变量.启用`,默认关。
- **每 5 楼才跑一次**:`if (SillyTavern.chat.length % 5 !== 0) return`。
- 范围是**滑动窗**:`[max(1, old - 2 - keepRecent*2), old]`,其中
  `old = message_id - keepRecent`。
- 那个 `*2`,注释写明是**因为没监听 `MESSAGE_SENT`**,所以要往回多探一段以跨过交错
  的用户楼。**这是对一个漏掉的事件的补偿,不是规则本身**——照抄它等于照抄一个 bug 的
  形状。
- **它从不全量扫**。所以一个关着清理的长局,把开关打开之后**不会被追溯清理**,只有
  向前推进的那个窗会被处理。

### 1.3 和回溯的耦合 —— 这是整件事的关键,而且它约束的是 `mes` 不是 variables

`cleanup/restore_variables.ts`:找到最后一个缺 `stat_data`/`schema` 的楼,用
`getLastValidMessageId` 回退到最近的快照,然后**从那个快照往前一条条重放
`updateVariables`**,把中间每楼的表重建出来。

> 所以上游的清理**是有损但可逆的**:快照间隔就是重放代价的上界。清理敢删,是因为
> 回溯能重算。

这一条决定了我们能不能照抄:**照抄删除而不照抄重放,得到的是一个不可逆的删除。**

**重放读的是每一层的 `mes`,不是它的 variables**(`restore_variables.ts` 循环体里
`message = SillyTavern.chat[i].mes`)。所以:

> **被清理的那 640 楼,真正不能动的是 `mes` 而不是 variables** —— variables 早就被剥
> 空了(合计 30 KB),而 `mes` 是重放的唯一原料。

这条推翻了一个方向相反的直觉("裁 `mes` 收益不大、variables 才是大头"),13 已就此
向 d7 收回他早前给窗口化的建议。**对我们的意义:任何未来的消息文本窗口化,都不能把
可能被重放到的楼的 `mes` 逐出**——回溯可达约一个快照间隔,从队尾算最远约 70 楼。

**而且窗口外的读是被设计出来的,不是意外**:上游有两个按钮收**任意绝对楼号**——
"快照楼层"(默认 '10')和"重演楼层"(两次输入,默认起点是
`getLastValidMessageId(目标)`),都没有边界检查。清理之后它们落在被剥楼上时,
`getLastValidMessageId` 会跳到更早的快照,**不报错,静默给出更早的状态**。

## 二、我们的实际开销(量出来的,和派单的前提不同)

### 2.1 那 677 楼在我们的日志里是什么样

```
文件                       18777 KiB / 677 楼
导入后事件                  2722 条
  iris/st-meta   677 条 ->  8831 KiB   ← 导入的表在这里(含用户行)
  iris/variables 677 条 ->  5487 KiB   ← hydrateVariables 重新挂出来的,prune() 只看这里
```

**两处都存了同一批表。** 抽 40 条 AI 行逐字节比对两侧:**39 条完全相同**。

它们不是纯冗余——`st-meta` 是**按行**(包含用户行,那是用户行投影的来源),
`iris/variables` 是**按候选**(swipe 一致性的来源)。粒度不同,但对 AI 行来说内容重叠。
**这 5487 KiB 是我们自己造的,上游没有对应物。**


### 2.1b 那 677 楼在磁盘上的分布(13 测,与本节独立)

```
677 楼   FULL 23   STRIPPED 640   SNAPSHOT 13   EMPTY 1

state       楼数     字节       均值
FULL          23   6.13 MiB   272.7 KiB
SNAPSHOT      13   2.14 MiB   168.4 KiB
STRIPPED     640   0.03 MiB     0.0 KiB      ← 640 楼加起来 30 KB
磁盘 variables 合计 8.29 MiB,活表 8.26 MiB
```

**36 个受保护的楼(5.3%)承担了 99.6% 的字节。** 他从三个文件的 SNAPSHOT 位置反推出
参数,和源码逐行对上:**间隔 50、按绝对楼号取模**(SNAPSHOT 落在 50/100/…/650),
**保留最近 20**(尾部 22 楼未动 = 20 加区间公式里 `-2` 的余量),**第 0 楼永不清理**。

> 两侧独立算出**同一个 6.6%**。楼数分类差 2:我按规则模拟(间隔/保留窗判定),他按
> 磁盘上的实际状态分类(`isMvuData` + `snapshot` 标记)。**差值没追,不要把两套数字
> 当成同一套。**

**推论(他的,我同意)**:任何"按字节阈值再砍肥楼"的方案,砍的都是**规则明确要保的
那 36 楼**——因为肥楼和受保护楼是同一批。

### 2.2 跑一遍我们现有的 prune()

```
prune() 清理了:0 层,报告 0 条
```

**这不是 bug,是正确结果。** 那份文件是**带着上游清理后的状态**进来的:643 楼的五个
键早就被删了,所以 `planPrune` 对它们判 `kept: nothing prunable left`;剩下约 34 楼
正好是快照/间隔楼,依规则保留。`prune.ts` 开篇写的「8.29 MiB 是清理**留下**的,不是
它removes 的」在这份数据上被验证了。

顺带把上游规则整份重跑一遍作对照:间隔 50、保留最近 20 的话,**只省 561 KiB(6.6%)**
——因为它已经被清理过了。

### 2.3 所以真实的量纲是

| | 上游 | 我们 |
| --- | --- | --- |
| 每楼是否物化表 | **是**,无条件(`update_variables.ts:1551`) | **否**,只在候选真的改了变量时写 |
| 不清理的长局开销 | O(N),677 楼约 133 MiB | O(变更数) |
| 清理后 | 约 8.5 MiB,**由约 34 个快照楼承担** | prune() 已具备同样的 O(N/interval) 性质 |
| 导入的长局 | 8.5 MiB | **14.3 MiB**(8831 st-meta + 5487 iris/variables) |

**两个不同的问题:**

1. **Iris 自己生成的长局** —— 我们的稀疏写入已经把它按变更数而不是楼数计价;
   `prune.ts` 覆盖剩下的部分。**这一半基本已经解决。**
2. **导入的长局** —— 开销比上游**高 68%**,而且高出来的那部分
   (`iris/variables` 那 5487 KiB)**是我们复制出来的,上游没有**。
   `prune()` 碰不到 `st-meta`(它只读 `iris/variables`,`entry.ts:835`),所以现有工具
   对这一半**一点作用都没有**。

## 三、提议

### 3.0 这个方案不是省空间的,先把框架说清

语料上「再跑一遍只省 6.6%」这个数很容易把整件事读成"不划算,不做"。**那是把方案的
目的读错了。** 那三个 677 楼文件**本身就是上游清理跑完的产物**,所以在它们身上再量
一次节省,量的是"清理跑了第二遍能多省多少"——答案当然接近零。

框架应该是两条,都不是省字节:

1. **与上游的保留窗同判(导入兼容)。** 一份从 SillyTavern 带过来的长局,已经被上游
   按"保留最近 20 + 每 50 一个快照 + 第 0 楼"清理过。我们的读路径必须和这个判定
   **一致**——哪些楼有表、哪些楼被剥空、回溯该落在哪个快照,都是上游已经写进那份文件
   的事实。判错了不会报错,只会静默给出另一个楼的状态。
2. **Iris 自生长局的前瞻。** 我们的稀疏写入让开销按变更数而不是楼数走,所以今天没有
   压力;但没有任何机制**保证**它一直如此(一张每轮都改变量的卡就是 O(N))。清理是
   那个上界的兜底,而不是当下的救火。

**所以验收口径不是"省了多少字节",是"我们对一份上游清理过的文件的判定,和上游一致"。**

### 3.1 `prune.ts`:扩展,不替代

它对 Iris 生成的长局是对的,规则也已经和上游对齐(五键、快照标记、保留窗)。要补的是
**它今天到不了的地方**,不是它的规则。

三处要改:

1. **默认从关改成开。** 上游默认也是关,但上游的关是安全的(有回溯);我们的关是让长
   局无限长。**开之前必须先有 3.2 的回取**,否则默认开就是默认丢数据。
2. **按楼而不是按回合**取模。今天 `planPrune` 用 turn,上游用**绝对楼号**——这一条
   现在有两重证据:源码里的 `(start + msg_index) % snap_interval === 0`,以及 13 从
   三个真实文件反推出的快照位置(50/100/…/650,全部能被 50 整除)。我在 prune.ts 里
   把这条记成有意偏离(「turn 是交换,所以不需要那个 `*2` 魔数」),那个理由仍然成立
   ——但**间隔的语义因此和用户在上游设的 50 不是同一个数**,一个交换是两楼,所以
   我们的 50 实际是上游的 100。**这条要么改,要么在设置里写明**;我倾向改,因为用户
   带着上游的心智模型过来。
3. **触发时机**:上游每 5 楼一次;我们今天在 `#settle` 里跑。频率没量过,列为待测。

### 3.2 回取,而不是具名拒绝(这是派单硬约束的落点)

`chat[i].variables` 是楼层变量的读通路,清掉的楼被显式读到时不得静默答空。两个选项:

- **具名拒绝**:诚实,但会让一张读历史楼的卡在长局里开始报错——而它在上游能用。
- **按需回取**:照上游的做法,从最近的存活表往前重放。

**提议回取**,而且我们做得到:日志里有每个候选的**回复原文**
(`assistant/message`),而 `recordVariables(turn, text)` 就是折叠入口。**上游能重放,
我们也能,而且用的是同一份材料。** 这也让 3.1 的"默认开"变成安全的。

代价:一次冷读要重放若干轮,上界是间隔。要量的是单轮折叠耗时(未测)。

### 3.3 导入侧的重复(这一项收益最大,而且和清理无关)

5487 KiB / 14.3 MiB = **38% 的日志是第二份拷贝**。三条路:

- **(a) 导入时不 hydrate,读时按需从 st-meta 取** —— 省 38%,但楼层变量的读路径要改,
  而那条路径刚在这轮修过两个 bug,我不建议现在动。
- **(b) hydrate 之后从 st-meta 里摘掉 `variables`** —— 省 38%,但 st-meta 是"原样带回
  未建模字段"的通道,摘一个字段会让往返不再逐字节相同,**972/972 那条不变式立刻破**。
- **(c) 不动,记账** —— 承认导入长局比上游贵 68%,写明原因是两种粒度各有消费者。

**我倾向 (c) 现在、(a) 以后**,理由:(b) 会破一条已经在保护真实用户数据的不变式;
(a) 是正确方向但要动刚修过的读路径,应该单独排期而不是搭在清理里。**这一项不该和
Tier 1.3 混做**,它只是量清理的时候撞见的。

### 3.4 可观测性

`iris/variables-pruned` 事件已经在写(候选、回合、删了哪些键、理由、时间),但
**除了测试没有读者**(`DEBUG-SURFACE.md` 记过这条)。清理默认开之后它就是"清理了什么
要有声音"的落点,应该接进 `debug.reports`——**不新建面**,理由同 DEBUG-SURFACE:
同一事实两个来源迟早不一致。

### 3.5 偏离记账

要写进 `DEVIATIONS.md` 的:①按楼 vs 按回合(若 3.1.2 不改);②不照抄 `*2` 补偿;
③回取的实现是重放而不是保留,所以**被回取的表是重算出来的,不是当时存的那一份**——
如果折叠有任何不确定性,重算值可能和原值不同。这条我**没有验证过折叠是否确定性**,
标为待测,而它是回取方案的正确性前提。

## 四、未查

- **折叠是否确定性** —— 3.2 的正确性前提,没验。若不确定,回取会静默给出与当时不同
  的值,那比答空更糟。**这是整份提议里最需要先验的一条。**
- **单轮折叠耗时** —— 回取的代价上界。
- **清理触发频率** —— 我们在 `#settle` 跑,没量过一局里跑多少次。
- **keep=20 / interval=50 是不是产品默认值** —— 13 明说这两个数是从**这台机器的三个
  文件**反推的实测值,他没读到 `自动清理变量` 的默认值定义(只读到消费点)。所以
  **别把它们当成上游的出厂默认**;要产品默认得去设置 schema 里找。
- **多 swipe 楼的两侧比对** —— 2.1 里 40 条有 1 条两侧不同,没追。可能是多 swipe 的
  形状差异,也可能是别的;**没查清之前不要把"39/40"当成"一致"**。
