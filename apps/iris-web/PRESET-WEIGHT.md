# message-preset 瘦身 —— 设计输入

一个会话里第一个楼层 frame 要下载 **2.29 MB**（`message-preset.js`）。它有内容哈希、
走我们自己的源、强缓存，所以只付一次——但那一次是「打开一个带界面的聊天有多慢」的
主要项。

`WINDOWING.md` 把它记成了另一本账。这份文档是那本账。

**这是设计输入不是规格**：给出成分、语料使用面、瘦身选项与各自的破坏面。

日期 2026-09-02。

## 口径

- 标 **[产物]** 的来自 `npm run build:sandbox` 后的 `public/sandbox/`，可复跑。
- 标 **[语料]** 的来自 19 张真实角色卡。
- 标 **[上游]** 的来自 JS-Slash-Runner 4.9.1 检出。

## 一、最要紧的先说：**这一节本身被更正过，先读更正**

> ### ⚠️ 更正（2026-09-02，f7 实测）
>
> 下面这一节原本的两条结论，**一条数错、一条判断错**，按惯例划掉保留而不是重写。
>
> **① 数错：不是各内联两次，是各被三个 `@font-face` 块引用。**FA6 的正式名、FA5 的
> 兼容名、v4 的 `FontAwesome`——**我少算了一整个 alias 家族**。f7 量到的冗余 base64 是
> **799,056 B**。
>
> （我原来量到 7 个 woff2 data URI、805,609 B、三个哈希各 2 次。**这两组数对不上**，
> 我没有强行和解——裁决走的方案不依赖哪个数对，但**下一个人如果要引用具体字节，
> 得先把这两把尺子对齐**。）
>
> **② 判断错：「破坏面：零」不成立。**我原写「同一份字节的副本，删掉一份不改变任何
> 行为」。**十个 `@font-face` 块没有两个是完全相同的**——它们是**三个不同的
> `font-family` 名指向同一个文件**。所以「删掉重复的块」删掉的是**别名支持**，
> 一张直接写 `font-family: FontAwesome` 或 FA5 名的卡会**静默地掉字形**。
>
> **③ 我的错法，和我在 §三 记的坏探针是同一个形状**：我对 data URI 的**内容**做了
> sha1，看到内容相同就判定「重复」——**但我没有检查外层声明是否相同**。
> **量了载荷，推断了容器。**
>
> ### 由此得到的判据，写下来给下一个人
>
> **「删重复」和「去重字节」是两个操作，只有后者的破坏面是零。**
>
> - **删重复**：减少声明数量 → 改变行为面（这里是丢掉别名）
> - **去重字节**：保留全部十个块与全部 family 名，让它们**指向同一份 base64**
>   → 零行为变化，省下同一笔 799 KB
>
> 判断「是否可去重」的正确判据是**按 sha1 比对块内容**，不是数声明次数。
>
> ### 现行裁决
>
> 走 **产物内 base64 去重**：十个块和全部家族名保留，构建期加一条牙断言钉住
> **字体字节集合不变**。落地后，原 §四 A 与它需要的语料普查一并作废。

## 四、瘦身选项与破坏面

### ~~A. 字体去重 —— 省 399,597 B（17.5%），破坏面：零~~ → **已被更正取代**

见 §一 的更正框。**这一条按原样是错的**：省的是 **799,056 B** 不是 399,597 B，
而且「删重复」的破坏面**不是零**（会丢掉 FA5 / v4 的 family 别名）。

**现行方案：产物内 base64 去重**——十个 `@font-face` 块和全部 family 名保留，
只让它们指向同一份 base64，另加构建期牙断言钉住字体字节集合不变。
**破坏面这才是零，省的是同一笔。**

### B. 砍掉 jQuery UI + touch-punch —— 省 316,938 B（13.8%）

[语料] **零使用**，两个独立探针都零：方法调用（`.draggable(` `.resizable(`
`.sortable(` `.datepicker(` `.dialog(` …）和类名（`ui-widget` `ui-icon` `ui-state-`）。

**破坏面：语料内零命中，但无机制保证。**上游给楼层 frame 注入它
（[上游] `iframe/third_party_message.html:4-6`），所以一张调 `.draggable()` 的卡
**在 ST 能跑、在我们这儿会 `TypeError`**。

这与 `WINDOWING.md` 里「用户行零接口」那条边界同形。**同样的处理方式**：可以砍，
但要让失败有声音——frame 里留一个具名的存根，被调用时抛
「这张卡用了 jQuery UI，Iris 的楼层预设默认不含它」，而不是 `undefined is not a function`。
**具名拒绝把一个「卡坏了」变成一个可上报的事实。**

### C. FontAwesome 字体子集化 —— 至多再省约 350 KB，**不建议做**

258 个字形只占全集的不足 13%，子集化收益很大。**但破坏面是真实且不可预测的**：

- 语料驱动的子集把**当前 19 张卡的字形集固化成了产品约束**；第 20 张卡用第 259 个
  字形就中招。
- **失败形态最坏**：缺字形不报错，只是渲染成一个空方框或豆腐块。既不抛异常、
  也不进任何日志——`OBSERVABILITY.md` 里「没有声音的失败」的教科书例子。

**要做的前提是先有「缺字形时具名报告」的机制**，而那个机制本身比省下的 350 KB 贵。
**建议排在 A、B、D 之后，或者不做。**

### D. 按卡预判注入 —— 我们能做而上游做不了的那一类

**懒加载在这里是不成立的**：卡的接口 HTML 在 parse 时就用 `$`，而 `<script src>`
在 `<head>` 里是**解析时就绪**的。任何「用到再加载」都晚于第一次使用。
（这与 `srcdoc.ts` 里 context 必须内联的理由是同一条：**parse 时刻不等人**。）

**可行的边界是按卡预判**：宿主组装 srcdoc 时扫这张卡的接口 HTML，决定注入哪几个库。

- **为什么我们能做**：srcdoc 由宿主拼装，库从我们自己的源按内容哈希提供。
- **为什么上游做不了**：[上游] 它的 8 个 `<script src>` 是写死在
  `third_party_message.html` 里的 CDN 直连，**没有组装这一步**。

  这正是升级账本里那类分歧：**不是我们更聪明，是我们多了一个上游没有的接缝。**

**破坏面：预判错了 = parse 时 `$ is not defined`**，而 `frame-entry` 的 try/catch
是运行时的、来不及存在（`METHODS.md` 记过这个形状：解析期失败只能从外面看）。

所以预判必须**宁可多带**：探针命中就带，不确定就带。按 §三 的分布，
「带 jQuery + Tailwind + lodash + zod，按需加 Vue 和 FontAwesome」已经覆盖 18/18。

### E. 拆成两级预设

核心（jQuery + lodash + zod ≈ 覆盖 15/18）与可选（Vue / Tailwind / FontAwesome /
jQuery UI）分开成两个内容哈希文件。D 的实现形式之一，**收益相同、粒度更粗**——
好处是文件数少、缓存条目少；坏处是两级之间的取舍点要靠猜。

**在 D 有实测之前，E 不比 D 好。**

## 五、和上游比，我们已经在哪一侧

[上游] 楼层 frame 的库是 `third_party_message.html` 里 **8 条 CDN 直连
`<script src>` / `<link>`**（7 条走 `testingcf.jsdelivr.net`，Tailwind 走扩展本地副本）。

| | 上游 | 我们 |
| --- | --- | --- |
| 来源 | CDN 直连 | 自己的源，内容哈希 |
| 缓存 | 由 CDN 与浏览器决定 | 强缓存、内容哈希、可离线 |
| 首包 | 8 个请求，跨 3 个主机 | 1 个请求 |
| **能否按卡裁剪** | **不能**（写死在静态 HTML 里） | **能**（宿主组装 srcdoc） |
| 版本 | 无版本 CDN tag，随时漂移 | 精确 pin 到用户机器上装的那版 |

**「第一口 2.29 MB」是我们自己的问题，也因此是我们能自己修的问题。**上游那 8 个请求
的总量并不更小，只是被拆散在 CDN 上、由不知情的第三方决定缓存策略。

## 六、建议顺序

1. **A′ 产物内 base64 去重**（取代原 A）—— 省 **799,056 B ≈ 34.9%**，保留全部十个
   `@font-face` 块与全部 family 名，破坏面零。**先做。**
2. **B 砍 jQuery UI + touch-punch** —— 再省 316,938 B（13.8%），配一个具名存根让失败
   有声音。
3. **D 按卡预判注入** —— 结构性收益，且是升级账本上的一条真分歧。**缓排**：
   A′+B 已拿下大头，而 D 的边际主要是 3/18 卡才用的 Vue（109 KB），配不上
   「预判错 = parse 期死、try/catch 来不及存在」的风险面。**「宁可多带」是 D 的
   第一原则，先写死在这里。**
4. **C 字体子集化** —— 不做，除非先有缺字形的报告机制。

A′ + B 合计省 **1,115,994 B ≈ 48.8%**，把 2.29 MB 降到约 **1.17 MB**，
且**没有任何一张语料卡会察觉**（A′ 是同字节且家族名不变，B 是零使用）。

## 二之三、决定性的结构事实：这些不是我们多给的，是契约

[上游] `.reference/MagVarUpdate/webpack.config.ts:378-386`，MVU 的 externals 映射：

```js
const global = {
  jquery: '$',   lodash: '_',    showdown: 'showdown', toastr: 'toastr',
  vue: 'Vue',    'vue-router': 'VueRouter',  yaml: 'YAML',  zod: 'z',
};
```

**MVU 把这八个全部 externalize 到注入的全局**——它的 bundle 里没有它们的实现，
运行时从环境取。所以 `preset.js` 里的五个库**一个都不能砍**：砍掉任何一个，
13 张装了 MVU 的卡里那个脚本 frame 直接 `is not defined`。

这解释了为什么这一份没有冗余：**它不是「我们顺手多打包了些库」，
它是上游注入契约的实现。**

（顺带确认一个可能的误读：MVU 产物里 4 处 `_zod` **全是事件名后缀**
`COMMAND_PARSED + '_for_zod'`，不是 zod 的使用——真正用 zod 的是另一个远程脚本
`mvu_zod.js`，9–10 张卡各自 import。）

## 二之四、两件值得单独记的

### toastr：零字节供上，还接进了诊断

`EXPECTED_GLOBALS` 里有 `toastr`，但 `preset-entry.ts` **没有 import 它**——
[此处] `src/sandbox/frame-entry.ts:872` 用的是
`host['toastr'] = createReportingToastr(report)`，一个**适配器**
（`frame.ts:112` 的注释原话：「Seed `toastr`, which is an adapter rather than a library」）。

用量不小：**12 / 36 份卡脚本调 `toastr.xxx()`，MVU 产物引用 73 次**（仅次于 lodash）。

**所以一个被重度使用的依赖，我们用零字节供上，并且把卡的提示接进了自己的上报通道。**
这条属于升级账本：上游注入的是真 toastr 库，卡的提示只到屏幕上；我们的适配器让
同样的调用**同时成为一条可上报的诊断**。

### showdown 与 vue-router：具名缺口，不是静默缺口

两者都在 MVU 的 externals 映射里，也都在 `EXPECTED_GLOBALS` 里，但
`preset-entry.ts` **都没有 import**。

关键是 `EXPECTED_GLOBALS` 是**缺失报告清单**（`preset-globals.ts` 的注释写明
「The frame reports the missing names from this array」）。所以它们缺席时
**frame 会点名报出来**，不是静默失败。

[语料] 两者都零使用：`showdown.Converter` 在 36 份脚本里 **0** 命中，
MVU 产物引用 `showdown` **0** 次、`VueRouter` **0** 次。

**建议保持现状**：不为零使用的依赖引入约 100 KB 的 markdown 库，让它继续被**报为缺失**，
等真有卡撞上再补。**这正是「拒绝要点名」比「预先满足一切」便宜的地方。**

## 二之五、瘦身选项

**没有可砍的。**五个库全部被 MVU externalize，语料里 jQuery/lodash/zod 三个还有大量
卡内联直接使用。

唯一查过的替代方案：
