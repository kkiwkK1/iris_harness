## 一、现状：我们已经在小规模复现上游的毛病

### 宿主暴露的设置面（[此处] `packages/iris-protocol/src/rpc.ts`）

| RPC | 载荷 | 覆盖的意图 |
| --- | --- | --- |
| `settings.get` / `settings.set` | `GenerationSettings`（12 字段） | 路由 + 采样 |
| `connection.list/save/delete/activate` | `ConnectionProfile` | 端点+模型+预设成套切换 |
| `worldbook.globalSelect` | `{ names: string[] }` | 世界书**选哪几本**（不含扫描参数） |
| `script.setEnabled` / `setDocumentGrant` / `setScriptsAllowed` | 每卡策略 | 脚本与授权 |
| `script.setExtensionSettings` | 每卡分区 | 卡自己的配置 |

`GenerationSettings` 全部 12 个字段（`views.ts:467-480`）：
`provider` `model` `temperature` `maxTokens` `topP` `topK` `minP`
`repetitionPenalty` `frequencyPenalty` `presencePenalty` `seed` `stop`。

**十个里有九个是采样参数。**

### 界面侧现在长什么样（[此处] `src/app/SettingsDrawer.tsx`）

```
ConnectionPanel（独立组件）
Section「Route」
  Provider / Model
  Temperature / Reply length cap / Top-p / Repetition penalty
  ▸ More parameters（折叠）
      Top-k / Min-p / Frequency penalty / Presence penalty / Seed / Stop at
Section「Reading」
  Theme / Prose size / Line length
```

### 这一节的结论

**我们的面板是按存储形状组织的，不是按意图。**「Route」区里同时装着「我在跟哪个模型
说话」（意图 #1）和九个采样参数（意图 #9）——**前者是每个人的第一个动作，后者
[宪章 §Sampling is used at a rate of zero] 量到的用量是零。**

已经做对的一半：采样的后六个**已经折叠**在「More parameters」后面。
方向对，只是折得不够——`temperature` / `topP` / `repetitionPenalty` 仍在第一屏，
而它们和被折叠的那六个属于同一个意图、同一个零用量。

**所以第一件要做的事不是加功能，是把 #1 和 #9 分开。**

## 二、靶子：上游那个「互相覆盖」具体是什么

宪章 [§#2 is the intent most in need of merging] 说「两处 `openai_max_context` 依加载
顺序互相覆盖」。我把这条的机制量到了，比那句话更狠。

### 覆盖表是显式存在的，有 102 项

[上游] `openai.js:298` 有一张表，注释写明它是什么：

```js
/**
 * preset_name -> [selector, setting_name, is_checkbox, is_connection]
 */
export const settingsToUpdate = { ... }
```

**这就是「加载一个预设会改写哪些设置」的清单。**我数了：

```
键数                        102
其中标记 is_connection 的     55
```

应用点在 [上游] `openai.js:4924`，逐键写进 `oai_settings` **并同步 DOM**。

**含义**：用户在设置面板里调过的值，**换一个预设就有 102 项被静默改写**——
其中 55 项是连接类，**包括他在跟哪个模型说话**。

这直接坐实宪章的意图 #1（「which model I'm talking to」散在 API 面板 + 预设 +
`custom_url`/`custom_model`）：**那不是三个地方各存一份，是第三个地方会覆盖前两个。**

### 还有第三个写入者，宪章没提到

[上游] `openai.js:5572-5587`：**选一个模型会给上下文上限设 `max` 属性，然后夹取当前值**。

```js
$('#openai_max_context').attr('max', contextSize);
oai_settings.openai_max_context = Math.min(Number($('#openai_max_context').attr('max')),
                                           oai_settings.openai_max_context);
```

所以「我能记住多少」这个值有**三个写入者**：设置文件、预设、**以及选模型这个动作本身**。
第三个既不在任何一个格式化面板里，也不在预设里——**它是另一个面板的副作用**。

**这才是「按存储位置组织」的完整代价**：用户要回答一个问题，不仅要访问四个面板，
还得知道第五个面板的一次点击会悄悄改掉答案。

## 三、IA 设计

宪章的十项意图，落到我们的实际数据源上。**成本分三类**：

- 🟢 **零成本接线**——RPC 已在，只是没接进面板或分错了区
- 🟡 **需要新 RPC**——宿主侧没有这个面
- ⚪ **主动不建**——[宪章] 量到零，写明理由（「主动不修」体例）

| # | 意图 | 数据源 | 成本 | 回指 |
| --- | --- | --- | --- | --- |
| 1 | **我在跟哪个模型说话** | `connection.*` + `settings.provider/model` | 🟢 | [宪章 §十项 #1] 6 次改动，人人的第一个动作 |
| 2 | **它能记住多少** | `settings.maxTokens` 🟢 + 阅读窗口 N 🟡 + frame 预算 🟡 + 世界书预算 🟡 | 🟡 | [宪章 §#2] 四个面板，两个互相覆盖 |
| 3 | **世界书什么时候触发** | `worldbook.globalSelect` 🟢 + 扫描参数（budget/depth/whole-words）🟡 | 🟡 | [宪章 §十项 #3] 9 次改动，并列最多 |
| 4 | **屏幕上有什么** | 界面本地（theme/size/measure）🟢 + 楼层号/耗时 🟡 | 🟢🟡 | [宪章 §十项 #4] 9 次改动 |
| 5 | **提示词怎么装配** | `script.getPreset`（只读）🟡 | 🟡 | [宪章 §十项 #5] 3 次但最重 |
| 6 | **思维链怎么处理** | 有 `Reasoning` 组件，设置未暴露 🟡 | 🟡 | [宪章 §十项 #6] 3 次，埋在 User Settings |
| 7 | **什么会自动发生** | `script.setEnabled` / `setScriptsAllowed` / `setDocumentGrant` | 🟢 | [宪章 §十项 #7] 12 次行为改动的大头 |
| 8 | **我是谁** | 人格，宿主侧无 | 🟡 | [宪章 §十项 #8] 3 次改动 |
| 9 | **回复有多随机** | `settings` 的九个采样字段 | 🟢**但要收起来** | [宪章 §Sampling…zero] **0 次改动** |
| 10 | **文本补全的格式化** | —— | ⚪ **主动不建** | [宪章 §十项 #10] 6 次改动**且全部无效** |

### 顶层分区建议

宪章的十项是**意图清单**，不是分区。落成面板需要合并——按「一次会话里什么时候会碰它」：

```
① 说话对象     ← 意图 1        每次换模型都碰
② 记忆与预算   ← 意图 2、3      长局用户常碰
③ 阅读         ← 意图 4         视觉偏好，改一次用很久
④ 卡与脚本     ← 意图 7         按卡授权，装新卡时碰
⑤ 人格         ← 意图 8
   ▸ 高级
     提示词装配 ← 意图 5
     思维链     ← 意图 6
     采样       ← 意图 9        默认折叠
```

**意图 10 不出现在任何分区里**，理由见下。

### 两条设计决定

**① 意图 2 必须合并成一个区，这是整份 IA 收益最大的一处。**

宪章说得对，而我量到的机制让它更硬：「能记住多少」在上游有**三个写入者**（§二）。
我们如果把 `maxTokens`、阅读窗口 N、frame 字节预算、世界书预算分放四处，
**就是在自己身上重造那个问题**——而且我们的四个数还互相作用
（`WINDOWING.md` 已论证：阅读窗口决定挂载量，frame 预算决定其中多少能建界面）。

**一个区，四个滑块，一句话说清它们的关系。**

**② 我们不做上游的覆盖表。**

上游的 102 项覆盖是「预设是一个完整快照」这个设计的必然结果。我们的
`ConnectionProfile` 已经是「端点+模型+预设成套」（`rpc.ts:72-75` 的注释写明
「switching a connection is switching all」），**但它是显式的一件事，不是 102 次静默改写**。

**这条要写进升级账本**：不是我们更聪明，是**我们把「成套切换」做成了一个有名字的对象，
而上游把它做成了一张覆盖表**。有名字的东西可以在界面上说「切换这个会改变以下三项」；
一张 102 项的表只能默默执行。

## 四、主动不建的，及其理由

「主动不修」体例：写明为什么不建，而不是留白。

| 不建的 | 理由 | 回指 |
| --- | --- | --- |
| **文本补全格式化面板**（context / instruct / sysprompt） | [宪章 §十项 #10] 量到 **6 次改动且全部无效**——用户走纯 Chat Completion，这三个面板在他的路径上零效果。**建一个零效果的面板，比不建更糟：它会让用户以为自己配置生效了。** | SETTINGS.md §十项 #10 |
| **采样参数的独立分区** | [宪章 §Sampling…zero] **0 次改动**。不是不做——**字段保留、可访问、但默认折叠在「高级」里**。删掉会伤到调采样的少数用户，摆在第一屏会误导多数用户。 | SETTINGS.md §Sampling |
| **102 项预设覆盖表的等价物** | 见 §三 决定②。我们已有 `ConnectionProfile` 这个具名对象，不需要再造一张隐式覆盖表。 | 本文档 §二 |
