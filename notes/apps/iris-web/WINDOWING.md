# 阅读视图窗口化 —— 设计

`RENDER.md` 的「Windowing」一节立了主张：外壳照上游形状（尾 N + 显式按钮），frame 侧按
字节预算。这份文档是那个主张的**设计**：N 取多少、预算超了怎么办、窗口滑动时 frame 的
生死、以及窗口外的接口块如何处理。

**这是设计不是规格**：给出决定与理由，实现形状由实现者定。

日期 2026-09-02。

## 口径

- 标 **[上游]** 的行号在 `E:/sillyTavern/SillyTavern/public/` 下。
- 标 **[此处]** 的是本仓库写作时的状态。
- 标 **[语料]** 的来自 19 张卡 / 31 个聊天的实测。
- 参数节里标 **[待填]** 的等 3e 的测量。

## 一、先纠正一处范围：没被窗口化的是三层，不是一层

`RENDER.md` 说「Iris 没有外层窗口」，指的是阅读列表。**列表不是最外层。**

| 层 | 现状 | 出处 |
| --- | --- | --- |
| **① 传输** | 整份聊天过线，且**每次都过** | 见下 |
| **② 挂载** | `ChatPane` 映射每一条消息 | [此处] `src/app/ChatPane.tsx:137-150` |
| **③ frame** | `render-window.ts`，内层窗口，**没有可嵌的外层** | [此处] `src/sandbox/render-window.ts` |

第 ① 层的证据 [此处] `packages/iris-protocol/src/`：

```ts
// views.ts:53-60
export interface ChatView { chatId, title, characterId?, messages: MessageView[], variables? }

// events.ts:38  —— 一轮生成结束
| { type: 'stream.end', chatId: string, turn: number, view: ChatView }
// events.ts:42  —— 编辑、swipe、删除
| { type: 'chat.updated', chatId: string, view: ChatView }
```

`stream.text` / `stream.reasoning` 只带增量（便宜），但 **`stream.end` 和 `chat.updated`
各带一整份 `ChatView`**。所以在 677 楼的聊天上，**每完成一次回复、每改一次消息，677 条
消息全部重新序列化过线一遍**。

脚本快照同理：`context.ts:96` 的 `chat: entry.toFile().messages` 也是整份，**且每行还挂着
那一楼的候选变量数组**（见 `FLOOR-VARIABLES.md`）。

### 这一层要不要现在做：**不做，但要现在点名**

- 第 ② 层**不需要任何协议改动**——客户端手里已经有全部消息，窗口化是纯本地的取舍。
- 第 ① 层需要新 RPC 和增量事件，是**另一个项目**，而且它的收益是序列化与带宽，不是
  渲染。

**建议：这一版只做 ② 和 ③，不加「按范围取楼」的 RPC。**理由是加了也没有消费者——
第 ② 层用不上它。**先把它写下来，是为了防止 ② 做完之后有人以为窗口化完成了**：
渲染成本降了，过线成本一点没降。

第 ① 层的实际代价 **[待填]**，等 3e 的单楼字节数。

## 二、外壳形状

### 决定：尾 N 条 + 显式按钮，不做无限滚动

照上游 [上游] `script.js:1475-1488` / `:1431-1473`。**论据不是「上游这么做」，而是上游
自己的 `loadUntilMesId`**（`public/scripts/power-user.js:2800-2812`）——它把「跳到第 N 楼」实现成
反复调用「加载更多」，这证明按钮语义足够支撑跳转，不需要滚动监听。

### N 取多少

**取 100，与上游相同。**

三条理由：

1. **上游的默认值就是 100**（[上游] `power-user.js:133` `chat_truncation: 100`），
   用户实测值也是 100（没改过）。**从 ST 迁过来的读者对这个数是有校准的。**
2. **第 ② 层的成本单位与上游同构**：一条消息的 DOM 与 markdown 渲染成本大致均匀。
   分歧发生在第 ③ 层（frame 的成本按字节差四个数量级），**不是这一层**。
   在成本单位相同的地方跟着上游走，把分歧留给成本单位真的不同的地方。
3. 用户语料里 31 个聊天只有 1 个超过 100 楼（677 楼那个），**所以 N=100 对 30/31 是
   恒等变换**——它保护的是最坏情况，不打扰常态。

### `0` 的语义必须是「全部」

上游 `power_user.chat_truncation || Number.MAX_SAFE_INTEGER`（[上游] `script.js:1477`）：
**滑块拖到 0 表示不截断**。`render-window.ts` 的 `depth: 0` 已经是同一个约定
（[此处] `render-window.ts:40-45` 有注释钉住它）。**两处必须同义**，否则同一个数字在
两层窗口里意思相反。

### 加载更多的语义

- 每次再加 **N 条**（与初始窗口同值），到 0 时移除按钮 —— [上游] `:1447` `:1462`
- **滚动位置补偿**：上游只在按钮当时可见时才补（`:1445` 先测 `isElementInViewport`，
  `:1466` 才用）。这行是防「用户没在看顶部时内容突然长高把视口推走」。**照抄，
  并在注释里写明它防什么**——照抄一行防御性代码而不知道它防什么，下次重构就会删掉它。

## 三、frame 字节预算

`RENDER.md` 已定：**2 MiB**，理由是同一个 N 下不同聊天的渲染字节差三个数量级，而最坏
的那个聊天**整个落在 100 楼窗口内**，所以按条数限根本不保护它。

这份文档补的是**预算怎么花**和**花完了怎么办**。

### 花的顺序：从最新一楼往回

读者在看的是最新的那一屏。**预算自最新楼向前逐楼扣减，扣完为止。**

### 不变量：**往回加载永远不夺走已有的 frame**

这是这一节唯一的硬约束。

用户点「加载更多」，新挂载的 100 条里可能有大量接口块。如果预算是全局重算的，
**新挂载的旧楼可能把读者眼前正在用的面板挤掉**——一个卡片状态面板在用户往回翻历史时
突然变成占位符，是比「旧楼没有面板」糟糕得多的体验。

所以：**已经建成的 frame 不因窗口扩大而被回收**；新进入挂载区的楼只能花剩余预算。
预算只在**窗口收缩**（消息被卸载）时归还。

### 超限的降级：具名，不静默

预算耗尽后，接口块**不静默消失，也不退回显示原始代码块**。

不退回代码块的理由：那正是上游关掉渲染时的行为，它会把一大段 HTML 倒进阅读视图——
对读者是噪音，而且**看起来像卡坏了**，与 `OBSERVABILITY.md` 记的「卡作者的 fallback
盖过我们的拒绝」是同一个病。

**该做的是一个具名占位**，说清三件事：
1. 这里**有**一个界面（不是没有）
2. 它**为什么**没渲染（渲染预算已用尽）
3. **怎么办**（就地渲染这一个）——按楼的显式放行

第 3 条让预算成为默认而非上限：读者永远能拿到他真正想看的那一个，代价是他自己点的。

> 这与 `SANDBOX.md` 的按卡授权同形：**默认拒绝 + 用户可就地放行 + 拒绝时点名原因**。
> 拒绝不是终局答案，是把选择交回去。

### 预算只数 AI 楼

[语料] AI 楼中位 **9.6 KiB**，是用户行的 **114 倍**。用户行相对而言是免费的。

所以**预算按 AI 楼计**，用户行不扣减。这不是优化，是让预算数字有意义：把用户行算进去
会让同样的 2 MiB 在不同对话里代表差很多的内容量。

> **这个决定有一条边界，写出来是因为它没有机制保证。**
>
> [语料] **189 个渲染后接口楼里，用户行为 0。**而且这个零不是空转出来的——
> 语料里有 **73 条正则脚本挂在 `USER_INPUT` 上（11 张卡）**，用户行的渲染管线是活的、
> 跑完了，仍然零接口。
>
> **但没有任何东西拦着一张卡把用户消息渲染成一个界面**：`applyRegexScripts` 对
> `USER_INPUT` 与 `AI_OUTPUT` 一视同仁。所以这条是**语料内零命中 + 无机制保证**，
> 不是不变量。
>
> 含义有二：①「用户行免费」在今天的语料上成立，将来可能不成立；
> ② 如果实现时要为「frame 只开在 AI 楼」写断言，**这条声明就是它的依据，
> 而断言本身会是那个缺失的机制**。

### N=100 与 2 MiB 在这个语料上几乎是同一条线

[语料] 100 楼窗口约 **2.1 MiB**。两个约束在用户的实际数据上重合。

**那字节预算还有什么用？**用处不是它更紧，是它**有上界而 N 没有**。
`RENDER.md` 已经量过：语料里最坏的那个聊天**整个落在 100 楼窗口内**，所以 N 对它
零保护。两者重合是这一份语料的性质，不是结构性质——**换一张卡就可能不重合，而只有
字节那条在任何语料上都有界**。

### 接口判据：用上游那个（189 楼），不用放宽的（235 楼）

[语料] 两个判据数出的接口楼数不同：上游 `is_frontend` 数出 **189** 楼，放宽后 **235** 楼。

> **⚠️ 这两个数的尺子是「渲染后」，不是「存盘」。**接口块是卡的**正则脚本在渲染时
> 生成的**——直读磁盘上的 `.jsonl`，用同一个 `is_frontend` 判据只命中 **1** 行
> （我扫过全部 31 个聊天 2454 条消息，另单独扫了 `swipes`），存盘层里的是 1111 个
> `<StatusPlaceHolderImpl/>` 占位符，经 display 正则展开成 HTML 后才有一部分命中判据
> （所以 1111 > 189 也合理）。
>
> **直读存盘会得到一个干净的、完全错误的零。**下一个人量这类数时先问：
> 我量的是渲染前还是渲染后。

**预算记账用上游那个。**理由是判据要和被限制的东西对齐：预算限的是**实际会建出来的
frame**，而只有上游判据命中的楼才会建 frame。用 235 记账会为 46 个不会建 frame 的楼
预留额度——**预算就不再等于它声称限制的那个东西**。

那 46 楼的差不是噪音，它回答的是另一个问题：**「当作纯文本显示时看起来像不像坏了」**。
那是「要不要把裸 HTML 倒进阅读视图」的问题（见 §三降级一节），**不是窗口化的问题**，
不该折进这个预算。

```

**复核当时（瘦身后）：**

**关键是三者的缓存性质不同**：

| 件 | 大小 | 怎么进 frame | 缓存 |
| --- | --- | --- | --- |
| **bootstrap** | **38,543 B** | **内联进 srcdoc**（`srcdoc.ts:131-184`，`escapeClose(bootstrap)` 放进 script 元素） | **无** |
| context 快照 | 通常 <1 KiB，最坏单楼 283 KiB | 内联（`srcdoc.ts` 的 `context` 注释自陈「paid per frame with no caching」） | **无** |
| srcdoc 包裹层（doctype/meta/CSP/token/reset） | ~1 KiB | 内联 | **无** |
| preset | 725 KB | `<script src>`，内容哈希命名 | 有（同 URL） |
| message-preset | ~~2.29 MB~~ → **1.47 MiB** | 同上 | 有 |

**所以每个 frame 的不可缓存固定开销 ≈ 42 KiB**（bootstrap + 包裹层），与卡自己的
markup 无关。

> **而下面所有推导在这个量级上都不敏感**。写死小数只会让文档比事实先过期。

> 一个界面帧本来每帧就要取 message-preset **1,658,336 B** + 成员表 **56,908 B**，
> bootstrap 这 53,802 B 是其中的 **3.0%**，量级和机制都与成员表相同。

### 两条由这个数导出的结论

**一、预算必须按整份 srcdoc 记账，不能只记卡的 markup。**

否则每个 frame 系统性少算约 42 KiB。二十个 frame 就是约 840 KiB 被漏在账外——
**超过预算的三分之一**。这与 §「判据选上游那个」是同一条原则的另一面：
**预算要等于它声称限制的那个东西**，而那个东西是 frame 的总重量，不是卡写了多少字。

**二、数量闸是必需的，且它的位置可以算出来。**

```
2 MiB / 约 42 KiB ≈ 49 个 frame
```

**五十个 frame 上下，固定开销单独吃光整个预算，卡的内容一个字节都放不下。**

所以数量闸不是「可能还需要」，是**结构上必需**——一个纯字节预算在 frame 变多时会
退化成「全是脚手架，没有内容」。

建议取值：**上限 20 个 frame**。理由是在 20 处固定开销占约 840 KiB（41%），
留 1.2 MiB 给内容；再往上固定开销的占比增长很快，而**同屏 20 个活面板已经远超任何
阅读场景**。这个数是从上面两个实测值推的，不是拍的；但它是**取舍点不是阈值**，
调整时把两个实测值一起改。

## 四、窗口滑动时 frame 的生死

**结论：不需要新机制。**这正是 `RENDER.md` 那条生命周期裁决在等的东西。

`RENDER.md` §Lifecycle 定的是「frame 活得和它那条消息被挂载一样久」，并写明
「**这依赖阅读视图被窗口化，而它没有**」。窗口化落地后：

| 事件 | frame 行为 | 机制 |
| --- | --- | --- |
| 窗口滑出（消息卸载） | **随之销毁** | React effect 清理，已有 |
| 加载更多（消息挂载） | 建 frame，受剩余预算约束 | 已有 + 本文档 §三 |
| 编辑 / swipe | 重建 | 已有：`useMessageInterfaces` 键在 `input.text` 上 |
| 取消编辑 | **不动** | 已有：文本没变，依赖没变 |

**要守住的是不要把窗口做成第二个生死判据。**`RENDER.md` 已经论证过「事件说发生了什么，
值说现在什么是真的」——窗口应当通过**改变哪些消息被挂载**来影响 frame，而不是通过
发一个「窗口变了」的事件让 frame 自己响应。前者是既有机制的自然结果，后者是新增一条
需要各自保证正确的通知链。

一处要注意：**`render-window.ts` 在 ② 落地后就该退场**。它的文件注释自己写着是
stopgap（`:12-16`「Until the view is windowed — a separate project」）。两个窗口叠着
不会更安全，只会让「为什么这一楼没有面板」有两个答案。**替换它，不要保留它。**

## 五、与 `splitAroundInterfaces` 的交互

**结论：不需要改它。**

[此处] `src/sandbox/frontend-blocks.ts:277-296` 的 `splitAroundInterfaces(source, blocks)`
是**纯文本切分**：把消息切成 `{kind:'text'}` 与 `{kind:'interface'}` 的有序段，
接口段落在它原来的位置上。它不知道预算，也不该知道。

两种情况分开：

**窗口外的楼**：根本没被挂载，`MessageInterfaces` 不会跑，`splitAroundInterfaces`
不会被调用。切分层面问题不存在——**但边界穿越的代价是真问题，见 §五之二。**

**窗口内但预算不够的楼**：`splitAroundInterfaces` **照常切分**，散文段照常渲染，
只有 `{kind:'interface'}` 段改渲染成 §三 的具名占位而不是 frame。

这条边界是干净的，值得写下来：**切分是文本层的，预算是资源层的，两层不交叉。**
预算的判断发生在「这个 interface 段渲染成什么」，不发生在「要不要切出这个段」。

好处是**占位符落在界面本来的位置上**——一条前后都有散文的消息，读者看到的是
「散文 / 这里有个界面（未渲染，点此渲染）/ 散文」，而不是散文被接起来、界面凭空消失。

## 五之二、边界穿越：接口不是集中在末尾的，所以这是主路径

我最初写的是「窗口外的楼没挂载，问题不存在」。**那句话太快了**，3e 的分布测量把它
否掉了：

> [语料] 接口楼的位置分布是**平的**：**76% 的接口楼在最新 20% 之外**；
> 三张卡近半数楼带接口，**最旧的几楼就有**。

含义：接口不是「最近几轮的状态面板」，是**散布全篇的**。所以读者往回翻历史时会**不断
穿越窗口边界**，而每次穿越如果都是一次完整重建，代价是实测过的：

> 一次 frame 重建 = jQuery + jQuery-UI + touch-punch + Vue + vue-router + FontAwesome
> + log.js + Tailwind + 卡自己的远程 HTML + 字体 + 3 个注入 blob，**全部重新拉取**
> （我在活的 ST 上抓过完整请求表，见 `RENDER.md` 的取消编辑一节）。

一张接口占半数楼的卡，往回翻两百楼就是**上百次这样的重建**。

### 决定：**穿越不自动重建**，占位是浏览历史时的正常状态

- **窗口滑出**：frame 销毁（既有 React effect 清理）。
- **窗口滑回 / 加载更多**：楼被重新挂载，但它排在预算队列的**后面**（预算自最新往回花，
  §三），所以通常**拿到的是占位符，不是重建的 frame**。
- **这是设计，不是降级。**往回翻历史的读者在读散文；他不需要四百楼前那个面板是活的。
  他真要那一个时，点一下占位符就地唤醒——**代价由他自己付，且只付一个**。

**明确否掉的方案：进入窗口即自动重建。**它在接口密集的卡上会把「往回翻」变成上百次
远程拉取，而收益是让读者没有要求过的面板活起来。

### 滞回：边界不能抖

窗口边界附近的小幅滚动不该反复建拆 frame。**销毁的边界要比建立的边界更外一圈**
（滞回带），这样在边界上来回一格不会触发任何生死。

**带宽现在可以定了**：一次穿越的代价是**约 42 KiB 的 srcdoc 重新内联 + 重新解析**
（§三），加上卡自己的 markup 和它的远程拉取。这个代价足够大，**滞回带值得存在**；
但它是常数级而不是随聊天长度增长的，所以**不需要很宽**。

> **2026-09-10：这一段的结论不变，构成变了，而且变得更贵。** bootstrap 外置后
> （§91）一次穿越是 **3.0 KiB 的 srcdoc 重新内联 + 重新解析**，加上
> **重新取 1.77 MB**（message-preset 1.66 MB + 成员表 56.9 KB + bootstrap 53.8 KB，
> 每个 frame 都是新的不透明源，一个都不命中缓存）。所以「代价足够大，滞回带值得存在」
> 这条**更成立**了，只是这笔钱从标记搬到了网络。**「不需要很宽」也不变**：它仍是常数级。

建议 **半屏**（约 5 条消息）。理由：小于一屏就够挡住普通滚动抖动，而更宽会让
「明明已经滑出视野的 frame 还活着」这件事变得可感——那是内存换体感，方向反了。

**这个数是取舍点不是阈值**，调整时和 §三 一起看（那里现在写着 3.0 KiB 的包裹层与
每帧 1.77 MB 的重取）。

### 这让占位符的质量从边角升级为主路径

76% 意味着**占位符是读者浏览历史时最常看到的接口形态**，比活面板更常见。

所以 §三 那三条（说清有界面 / 说清为什么没渲染 / 说清怎么办）不是错误提示的措辞
讲究，**它是这个功能的主要外观**。做成一个灰色的「[未渲染]」小方块就等于把 76% 的
接口楼变成噪音。

## 六、宿主侧要不要新 RPC

**建议：这一版不要。**

按范围取楼的 RPC（`chat.messages(chatId, from, to)` 一类）**只服务第 ① 层**，
而这一版不做第 ① 层。第 ② 层的窗口是纯客户端的——`ChatView.messages` 已经在手里。

现在加它的坏处是具体的：一个没有消费者的 RPC 会**被后来的人当成"窗口化已经做完了"的
证据**，而实际上它一次都没被调用。`METHODS.md` 记过同形状的一课——五个 handler 全部
实现、测试、且在 wire 上不可达。

**第 ① 层立项时需要的东西，一并写在这里，省得那时重新推导：**

1. **范围取楼**：`chat.messages(chatId, from, to)`
2. **增量事件**：`stream.end` 与 `chat.updated` 现在各带一整份 `ChatView`
   （`events.ts:38,42`）。第 ① 层的核心其实是这两个——**它们的成本与聊天长度成正比，
   且每轮都付**，比 `chat.open` 那一次性的成本高得多。
3. **脚本快照同样是整份**（`context.ts:96`），且每行挂着变量数组。它和 `ChatView`
   是两条独立的整份传输，**都要窗口化，且窗口边界必须一致**——否则卡能读到的楼
   和读者能看到的楼不是同一批，那会制造一类极难诊断的差异。

第 3 条是我认为第 ① 层最该先想清楚的：**两个窗口不一致比两个窗口都没有更糟。**

## 回合边界：向外取整，代价至多一条

[此处] `ChatPane.tsx:137` 按回合分组渲染，而窗口按消息计数——一个回合被边界切成两半
时怎么办。

**量过了：一个回合最多两条消息。**`lineTurns`（[此处] `packages/iris-app-service/src/entry.ts:116-136`）
每个回合最多产出一条 `user/message` 行和一条 `assistant/message` 行，后者还被 `seen`
集合按回合去重（所以 swipe 折叠成一条）。`groupByTurn`（[此处] `src/app/project.ts:85-96`）
按连续同 `turn` 分组，所以**组的上限就是 2**（开场白那组是 1）。

**所以：窗口边界向外取整到回合边界，代价至多多渲染一条消息。**这个决定不值得再想，
直接做。

## 快照的传输代价:第 ① 层第一次有数(浏览器实测,2026-09-03)

「未定」第 1 条("第 ① 层的实际代价未量")的一半现在有数了。**在真的
`sandbox="allow-scripts"` 不透明源 frame 里量的**,不是 Node——这一层的成本是浏览器
`structuredClone` 的成本,而 Node 的 clone 与浏览器的不是同一个实现。

两种形状**字节对齐**,各 2.00 Mi UTF-16 单位(= 4 MiB):

```
扁平字符串表 structuredClone            1.47 ms     ← 卡存储(localStorage)的形状
嵌套对象树   structuredClone           24.21 ms     ← 楼层变量表今天的形状
                                       比值 16.5x
同一棵树序列化后按字符串 clone           1.77 ms
那份文本整体 JSON.parse                 7.75 ms     （文本路合计 9.52 ms）
单楼(338 楼中的一楼) JSON.parse         0.01 ms
```

### 结论一:楼层变量表改以 JSON 文本携带,收益比 Node 数更大

49 在 `SNAPSHOT-TRANSPORT.md` 用 Node 量得 87.7 → 16.8 ms 并据此裁定改文本。浏览器侧
同向且更有利,**但要用对分母**:文本路的真实代价不是 `1.77 + 7.75 = 9.52 ms`——那是把
整局都 parse 了,**而没有卡会那样做**。卡按 `message_id` 问一楼,而单楼 parse 是
**0.01 ms**。

> 现实比较是 **1.77 + 0.01 ≈ 1.8 ms 对 24.21 ms,约 13×**,不是 2.5×。

`getVariables({message_id})` 的按需 parse + 缓存(缓存随快照一起丢)因此几乎免费。

### 结论二:卡存储**不**跟着文本化——一条撤回

我先前建议存储快照也搭 49 那班文本车。**按这组数撤回。** `localStorage` 的值本来就是
字符串,整份 store 是扁平 `Record<string,string>`,**已经在字符串速度上**(4 MiB → 1.47 ms);
再包一层 JSON 只会凭空多一次 parse。

同一组数也定了另一件:**存储不设单值上限**。壁纸那种 MB 级 data URL 是 memcpy 级,4 MiB
一次 1.47 ms。约束是整份 store 的配额(10 MiB,浏览器机制),不是单值大小。

### 判据:这组数区分不了什么

- **只量了 clone,没量 `postMessage` 的序列化与投递**。两者在同一次跨界里发生,而我只
  隔离了 clone。所以这些数是**下界**。
- **没量内存峰值**。4 MiB 的树 clone 一次意味着同时存在两份,而 20 个 frame 各一份的
  峰值没有量过。
- **单机单次,Chrome**。Firefox/Safari 未量。
