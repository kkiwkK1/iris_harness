## 4. 爱衣的 0% 轮：定案

### 4.1 §2.1 的假设，按它的字面表述，被推翻

假设是"MVU 的 `setExtensionPrompt` 注入落在 main 旁且每轮变"。
MVU 对主请求一次 `setExtensionPrompt` 都没调（§0.4，对部署中的 bundle 全文搜索
0 命中）。爱衣那张卡的两条脚本是 MVU 的 bundle 和一份 zod schema，
**两条都不向主请求注入任何东西**。

### 4.2 宿主自己装不出 0%

- **同状态装配两次：逐字节相同**（爱衣是 16 条会话里"不抖"的 11 条之一）。
- **11 对相邻轮里，第一处分叉最早出现在 `msg[6]`**，也就是第 59 427 字节
  之后——**从来没有落在前 64 token 之内**。
- 而 0% 要求分叉出现在第一个 64 token 块之内（§3.3(a)：命中按 64 对齐，
  所以任何 ≥64 token 的公共前缀都会回报 ≥64）。

**结论：0% 不可能由宿主这一侧装配出来。**

### 4.3 剩下的两个候选，以及能把它们分开的算术

**候选一：浏览器侧有东西落在头部且每轮变。** §6 实测了这条路径的代价：
一条每轮变的注入放在 `'before'` → 爱衣上界 **0.4%**，放在 `'after'` → **2.7%**。
所以**如果**有这种注入，0% 正是应该看到的形状。但 §4.1 说爱衣的卡没有这种注入。

**候选二：提供方没给。** 文档级依据两条：`前两次请求不会命中缓存`、
`缓存系统是"尽力而为"，不保证 100% 缓存命中`（引文见 `CACHE-TARGET.md` §1.2、§1.4）。
爱衣观察到的 0 / 31.4 / 0 / 45.2 / 0 / 74.7 交替，与"每轮的尾部都变 ⇒ 无法完整匹配
上一轮的前缀单元 ⇒ 要等公共前缀被检测并落盘之后的那一轮才命中"这一机制同形。

**`prefixHash` 这条线索本轮不能定案，而且理由本身是个发现。**
爱衣最后 4 个生成的 `prefixHash` 两两不同，看起来像"我们每轮都在改头部"。
但这与同一串里的回报**算术上不相容**：swipe 2 回报命中 7 424 token，
而 `prefixHash` 只覆盖前 4 096 字节 ≈ **1 138 token**
（110 562 B / 30 696 tok = 3.60 B/token）。若前 4 096 字节真的变了，
命中不可能超过约 1 138。两个前提必有一个错，而唯一与两个观测都相容的解释是
**`prefixHash` 变化来自路由而不是提示词**：`serialiseRequest`
（`fingerprint.ts:167-176`）把 `provider` 与 `model` 写在被哈希字符串的**开头**。
换一次模型就让 `prefixHash` 变，提示词一个字节没动。
而这些记录**没有 `model` 字段**（§0.1），所以本轮无法证实也无法排除。

### 4.4 "搬到尾部上界会到多少"——直接回答 C

用真实 `placementFor` 路径实测（§6）。爱衣：

| 一条每轮变的注入放在 | 上界 |
|---|---|
| `position: 'before'`（= `main.order − 1`） | **0.4%** |
| `position: 'after'`（= `main.order + 1`） | **2.7%** |
| `at-depth 0` | **74.7%** |
| `at-depth 2` | 72.8% |
| 无注入基线 | 74.9% |

**把一条每轮变的注入从 `'before'` 搬到 `at-depth 0`，上界从 0.4% 回到 74.7%，
也就是完全回到无注入基线。** 一条每轮变的 depth 注入**不要任何代价**：
74.7% vs 基线 74.9%，差的 0.2 pp 是它自己那 200 多字节进了分母。

### 4.5 爱衣今天真正的限制项，以及它能到多少

不是注入。**是那一块 depth 锚定的内容，而且它一条就是全部故事。**

每轮重发 **24 980 字节 / 约 7 140 token**，逐字未变（§2.2），
占每轮约 30 700 token 的 23%。两个反事实（都是实测，都报了被挪动的段数）：

| 反事实 | 爱衣 10 对真实相邻轮 | 合成 +1 轮 |
|---|---|---|
| 原样 | 67.2% – 73.7% | 74.9% |
| **把 depth 锚定内容整块删掉** | **92.8% – 98.7%**（10/10 对） | **97.5%** |
| **把它提到请求最前面**（只在它逐字稳定时才是收益） | **95.0% – 98.6%**（6/10 对）；另 4 对**塌到 5.2% – 6.2%** | **98.0%** |

**所以"靠搬位置到不了 95%"是错的**——我在拿到修正后的反事实之前起草了这句话，
它来自一个只挪动了"被目录点到名"的那部分 depth 段的旧数（82.8%）。
统一了归因解析器之后（§8.2），同一个反事实是 **98.0%**。

正确的结论分两半，因为那 4 对塌掉的对子说明了另一半：

1. **depth 锚定内容逐字稳定的那些轮，把它放进稳定前缀，上界到 95%–98.6%。**
   爱衣 10 对里有 6 对（10→12、14→16、16→18、20→22、22→24、24→27）是这一类，
   它们的租金都是 7 140 token。
2. **另 4 对（6→8、8→10、12→14、18→20）里这块内容自己变了**，租金掉到 4 694 token
   （变的那一段不再算进逐字重复的尾部）。把一块每轮变的内容提到最前面，
   上界从 ~68% 塌到 ~6%——**同一个操作，方向相反**。
   为什么会变：世界书的激活集随扫描窗口变化，历史短的时候某些关键词条目不触发。
   （对最新那一对做定点逐字比对：三块 depth 内容 8 223 + 4 020 + 7 114 = 19 357 字节
   **全部逐字节相同**，见 §8.1 的 `depth-diff` 命令。）

给 C 的一句话：**搬位置能把爱衣送到 95% 以上，但必须先分清哪一部分逐字稳定；
把易变的那部分一起搬上去会让结果比不搬还差一个数量级。**

## 6. 卡脚本注入实验：16 张卡，同一条注入，四个位置

用真实 RPC `script.setExtensionPrompt` 注册，落位由产品代码
`placementFor`（`service.ts:4273`）决定——**位置不是模拟的，只有内容是**。
内容形状照 MVU（一段稳定的 `<variable_rules>` + 一行每轮变的 `<current_state>`），
每个位置都跑两遍：内容在两轮之间**变**，和内容**保持不变**。

| 变体 | n | 上界均值 | 范围 | 第一处分叉落在 |

| 无注入（基线） | 16 | 41.1% | 7.6% – 75.3% | 各会话自己的原因 |

| `'after'`，内容不变 | 16 | 41.4% | 8.2% – 75.6% | 回到基线的原因 |

   `'before'` 落在 `system[3]`、`'after'` 落在 `system[9]`——两者都在

而"尾部"的正确写法是 `position: 'at-depth', depth: 0`，不是 `'after'`——
`'after'` 现在是 `main.order + 1`，在头部（§0.5）。**

## 7. 发现但没改

1. **卡脚本自己发起的生成完全不记账。** `script.generate` → `#sideGenerate` →
   `this.#stream({...})` **不传 `entry`**（`service.ts:3613`），
   而 `noteUsage` 与 `notePromptFingerprint` 都挂在 `entry?.pending?.turn` 上
   （`service.ts:3997`、`:4035`）。所以卡脚本的请求**不写 `iris_usage`、
   不写 fingerprint、不进用量页**。对 MVU 这类卡这不是边角：它每轮都会为
   变量更新再发一次请求（`invoke_extra_model.ts:511`），
   而 gemini 路径还会在最前面加一个 35 字符的随机 uuid 头
   （`invoke_extra_model.ts:44-46`，`_.times(4, () => uuidv4().slice(0,8)).join('\n')`），
   **那条按构造就会打掉自己的前缀缓存**。这些请求被 DeepSeek 计费，
   用量页上一条都看不到。→ "全 profile 95%" 这句话如果不加限定，
   说的是一个比用户账单窄的总体。
2. **`prefixHash` 的窗口里含路由。** `serialiseRequest`（`fingerprint.ts:167-176`）
   把 `provider`/`model` 放在被哈希字符串的开头，所以换模型让 `prefixHash` 变化
   而提示词没动——正好破坏该模块文档里写的判据（"两轮 `prefixHash` 相同而
   `cacheReadTokens` 为 0 指向提供方；不同则指向我们"）。§4.3 有一个只能这样
   解释的样本。`9f7bb46` 之后 `model`/`provider` 已单独记录，所以也可以选择
   "不改代码、在分析时减掉"。**这条直接影响 A 的分叉归因仪器，建议先裁决。**
3. **一个真实轮记录下来的 `budget.context` 是 32 768，而它实际按 2 000 000 装配。**
   `#itemizationOf` 的 `window` 参数在预览路径（`service.ts:3528`）传了、
   在**真实轮**路径（`service.ts:3410`）没传，于是回落到
   `this.#options.contextWindow`（`cordis.yml` 的 32 768）。
   实测：`银麒赎世` 装配 55 543 token，记录里 `budget {"context":32768}`、
   `overBudget false`（`overBudget` 是对的，因为真实窗口是 200 万）。
   凡是用这条记录当分母的地方（上下文容量胶囊）都会显示错的占用率。
4. **预览与真实轮的装配 token 能差 40%。** 同一条 `银麒赎世`：
   `prompt.itemize({chatId})`（预览）报 91 734 token，
   走 `chat.regenerate` 捕到的那次报 55 543 token。两者的 `generationType`
   不同（预设过滤不同）足以解释方向，但差 36 191 token 值得有人确认一次
   ——用户看到的是预览那个数。
5. **`{{get_message_variable}}` 与 `{{format_message_variable}}` 不是一回事。**
   MVU 教程教作者写的是 `{{get_message_variable::stat_data}}`
   （`doc/tutorial.md:43-47`），它按 `JSON.stringify` 展开（单行）；
   `{{format_message_variable}}` 按 `YAML.stringify` 展开并把前缀文本重新缩进
   （`macro_like.ts:49-77`）。`CACHE-PREFIX.md` §2 记的是 `format_` 那一个。
   两者体积与形状都不同，模拟或估算变量表大小时要点明用的是哪一个。

## 8. 仪器，以及它自己的弱点

### 8.1 跑了什么

```
npm run census:cache-cause                                 # 16 条会话，四种测量
IRIS_CENSUS_JSON=out.json node scripts/cache-cause-census.mjs
IRIS_CENSUS_CHATS='爱衣' node scripts/cache-cause-census.mjs
IRIS_CENSUS_INJECT=0 node scripts/cache-cause-census.mjs    # 跳过 §6
IRIS_PROBE_CHATS='爱衣' node scripts/cache-prefix-probe.mjs  # §8.1 的交叉校验
```

本轮跑完之后 `npx tsc --noEmit` 退出 0，
`node --test "packages/*/tests/**/*.test.ts" "apps/*/tests/**/*.test.ts"`
是 2994 项 / 0 失败 / 13 跳过——**没有改任何产品代码**，
两条只是用来证明"没改"这件事本身成立。

`scripts/lib/cache-host.mjs` 是 `cache-prefix-probe.mjs` 里那套 headless 宿主的
提取版本，**探针本体一个字节没改**（`git diff --stat scripts/cache-prefix-probe.mjs`
为空）：把一个在跑的仪器改写成 import 这个库，会在三个人并行编辑 `scripts/` 时
换来一个合并冲突，而换不来任何新测量。

**交叉校验：同一天、同一份语料，两套独立写的宿主装配出逐字节相同的请求。**
`IRIS_PROBE_CHATS='爱衣' node scripts/cache-prefix-probe.mjs` 与本普查
在 8 对重叠的相邻轮上，body 字节数与公共前缀**完全一致**，例如：

| | 探针 | 本普查 |
|---|---|---|
| 10 → 12 消息 | `89829 → 94641`，前缀 `63858` = 67.5% | `89829 → 94641`，前缀 `63858` = 67.5% |
| 24 → 27 消息 | `107555 → 111549`，前缀 `81610` = 73.2% | `107555 → 111549`，前缀 `81610` = 73.2% |

**这个一致证明的是宿主搭建与回溯步骤对齐，不是前缀算术正确**：
`commonPrefixBytes` 是从探针**逐字复制**过来的，两边跑的是同一段代码，
所以它们在这一层不可能不一致。真正被校验的是两份 `buildHost`、
两套摘尾/回溯序列产出同一个请求。

对比 `CACHE-PREFIX.md`：它记的爱衣 `22 → 24` 是 86.2%，本轮同一对是 74.1%
（body 口径）。**差异不是仪器分歧，是语料长大了**——上面这张表说明两套仪器
今天读同一份语料给出同一个数（§3.2：depth 0 那块从 5 367 字节到 16 498 字节）。

定点逐字比对（爱衣最新那一对的 depth 块是否真的没变）是一段临时脚本，
不入库；它做的事是：摘尾部回复 → 装配 → 再删两条 → 装配 → 把两次里
≥3 000 字节的 `msg` 段从尾部对齐逐字比。结果：
`8 223 / 4 020 / 7 114 字节三块全部 IDENTICAL`。

### 8.2 一个已经修掉的仪器缺陷，以及它改掉了哪些数

第一版把归因写成了三份：`firstDiff` 有自己的兜底、`wasted` 有自己的兜底，
而两个反事实闭包（`ceilingWithout` / `ceilingHoisting`）还在调**原始标签器**。
后果是 `ceilingWithout(cause === 'worldInfoBefore')` 在那四条
"分叉就在 `worldInfoBefore`"的会话上**一个段都没删**，然后把原样的上界
当成反事实报了出来——读起来正好是"搬它没用"。

**一个用"什么都不动"来回答"动了会怎样"的数，比没有数更坏。**
修法是把三份归因合成一个 `resolve`，并让每个反事实**报出它真的动了几段**
（`touched`，报告里的 `n=`）。被这个缺陷改掉的数：爱衣"提到头部"
从 82.8% 变成 **98.0%**，`OVERLORD不死者之王`"删掉 wiBefore"
从 9.6%（假的）变成 **46.5%**，而 §4.5 一条已经起草好的结论
（"靠搬位置到不了 95%"）被推翻。

### 8.3 归因的可靠性分三层，报数时不要混

1. **字节层（最可靠）**：公共前缀长度、分叉字节位置、逐字重复的尾部大小。
   这些是从捕到的请求直接量的。
2. **宿主 itemization 层（可靠，但按 token 累加定位是近似的）**：
   一个 `system[i]` 块属于哪一段，用宿主自己的 itemization 行按累计 token
   偏移定位（`systemSectionAt`）。它足以指认一段 4 527 token 的
   `worldInfoBefore`，不足以区分两段相邻的 5 token 小块。
3. **目录标签层（提示，不是结论）**：段落名字与宏名靠"最长字面片段"匹配。
   **本轮抓到一例贴错**：`Sgw又看一集` 抖动的那块，字节证据是
   `Avatar_Map` 里的 `{{random::…}}`（书里就这么写的），
   而标签器给出的宏是 `{{get_message_variable}}`——它匹配到了同一本书里
   **另一条**条目。所以排行榜里"涉及宏"那一列是**指示性的**，
   §5.1 的字节引文才是证据。
   卡的**内嵌**世界书更是标签器完全看不见的一类：它 base64 编在卡 PNG 里，
   `grep -a` 整个 profile 都搜不到——这就是第 2 层存在的原因。

### 8.4 这份普查看不见什么

- **卡脚本真实注入的内容。** `ChatEntry.extensionPrompts` 是内存里的 `Map`

  所以本文件关于抖动量的一切都是**下界**。
- **真实轮的历史上界。** §3.2：本文件的相邻轮是"今天重装旧历史"。
