# ≥95% 命中率怎么算达标：测量协议

> 2026-09-08。B（归因普查）写，给 C（缓存友好装配）与 D（历史侧字节稳定性）的 PR 报数用。
> 数据与归因见 `CACHE-CENSUS.md`；提供方语义的引文在本文件 §1，全部引自
> 2026-09-08 当天抓取的 DeepSeek 官方文档。
>
> **本文件先定"什么是达标"，再定"怎么量"。顺序是刻意的**：上一轮
> （`CACHE-PREFIX.md`）把六个真实轮次的命中率与九对相邻轮的上界并排列出来，
> 两列各自都对，但它们量的不是同一个请求（见 §4.2），于是"差距"那一列不成立。
> 协议要先说清测的是哪个总体。

> **外部路径的读法**：`service.ts:` / `translate.ts:` / `fingerprint.ts:` /
> `compaction.ts:` / `activate.ts:` 指本仓文件；`invoke_extra_model.ts`
> 属于 **MagVarUpdate**，不在本仓树上。

## 0. 一句话

> **达标 = 在一条按 §3 建好的会话里，连续 10 个符合 §4 纳入条件的生成，
> 提供方回报的 `prompt_cache_hit_tokens / prompt_tokens` 每一轮都 ≥ 95%，
> 且这 10 轮的合计也 ≥ 95%。**

"每一轮都"与"合计"两条都要，因为它们排除不同的失败：合计能被一轮 100%
和一轮 90% 平均掉，逐轮能被一轮 0% 直接判负——而 0% 轮正是这次要解决的形状
（`CACHE-CENSUS.md` §3：真实记录里 10 个生成有 5 个是 0.0%）。

## 1. 提供方语义：协议依赖的七条事实

全部引自 2026-09-08 抓取的 DeepSeek 官方文档。**每条都标了"文档说了什么"
与"文档没说什么"**，因为协议里有三处必须绕开文档的沉默。

### 1.1 命中的单位是 token 前缀，且必须"完整匹配"缓存前缀单元

> 缓存命中的前提是相应前缀已被"落盘"（写入硬盘缓存）。受 Sliding Window
> Attention 机制的影响，缓存前缀的存取与判别与之前有所不同。每条缓存前缀是一个
> 独立的完整单元。**后续请求只有在完整匹配缓存前缀单元时，才能命中缓存。**
>
> — <https://api-docs.deepseek.com/zh-cn/guides/kv_cache>，2026-09-08 抓取

> 注意，只有当两个请求的前缀内容相同时（**从第 0 个 token 开始相同**），才算重复。
> 中间开始的重复不能被缓存命中。
>
> — <https://api-docs.deepseek.com/zh-cn/news/news0802>，2026-09-08 抓取

`system` 消息在前缀之内，文档用例说得很直：

> 前两次请求完成后，系统会识别出 **system 消息 + user 消息中的\<财报内容\>** 为
> 缓存前缀单元，并进行落盘。
>
> — 同上 kv_cache 页，"举例 2"

**文档未说明**：前缀是整个序列化请求的字节前缀，还是只覆盖 `messages`。
也**未说明** `tools` / `response_format` / `temperature` / `max_tokens` /
`top_p` / `stream` / `seed` 是否参与前缀匹配——kv_cache 两个语言版本里
这些词的出现次数分别是 0/0/1/0/0/0/0，而唯一那次 `temperature` 只出现在
"输出仍受 temperature 影响"这句里，说的是输出而不是键。协议因此**不假设**
这些字段安全：§3 要求它们在整段验收里保持不变。

### 1.2 "公共前缀检测落盘"——第二个请求注定不命中

> 举例 2：用户第一轮请求的内容为 A + B，第二轮请求的内容为 A + C，则
> **第二轮请求无法命中缓存**，因为 A + C 不能完整匹配第一轮的缓存前缀单元
> （A + B）。但此时系统会识别到两轮请求存在公共前缀 A，并将 A 作为缓存前缀单元
> 落盘。当第三轮请求 A + D 到来时，能完整匹配 A 这个缓存前缀单元，可以命中 A 的缓存。
>
> — kv_cache 页，2026-09-08 抓取

> 在上例中，**前两次请求不会命中缓存。**

**这是协议里最重要的一条**，因为它说明"一条新会话的第 2 轮 0% 命中"是文档
写明的正常行为，不是缺陷。`CACHE-CENSUS.md` §3 里 `OVERLORD-沙盒` 的两轮
（0% 与 0%，且两轮的 `prefixHash` 完全相同）正好是这个形状。协议因此在
§4 里排除每条会话的**前两个**生成，而不是只排除第一个。

### 1.3 64 token 的块——文档已经撤掉了这个数，但语料还在按它对齐

当前 kv_cache 页只说：

> 按固定 token 间隔落盘：在长输入或长输出中，系统会以**一定的 token 数量**为间隔，
> 截取缓存前缀单元……

"一定的 token 数量"没有给值。全站唯一给了值的地方是 2024-08-02 公告页的脚注：

> 注1. 缓存系统以 64 tokens 为一个存储单元，不足 64 tokens 的内容不会被缓存
>
> — <https://api-docs.deepseek.com/zh-cn/news/news0802>，2026-09-08 抓取

而这一页自己声明价格已过期（"注 1: API 价格已做调整"），且它"不限流、不限并发"
的说法与现在的 `/quick_start/rate_limit`（并发 500 / 2500、超限 HTTP 429）
直接矛盾。**所以 64 是一条 2024 年的陈述，改写后的指南把它删掉了。**

**但语料量得出它还在生效**：本 profile 里 10 个生成回报的
`cacheReadTokens` 是 0、3 456、0、6 144、0、9 216、12 288、7 424、1 408、0，
**每一个非零值都是 64 的整数倍**（54、96、144、192、116、22 块）。
六个非零样本全部整除，这是对一条文档已不再作出的陈述的实测确认。

协议按 64 对齐算上界（`scripts/lib/cache-host.mjs` 的 `blockShare`：
`floor(prefixTokens/64)*64 / totalTokens`），并记一句：**若某次验收出现非 64
倍数的 `cacheReadTokens`，先改这里的常量，再谈达标**——那意味着提供方换了粒度。

### 1.4 缓存寿命：几小时到几天，尽力而为，构建耗时秒级

> 缓存系统是"尽力而为"，**不保证 100% 缓存命中**
> 缓存构建耗时为**秒级**。缓存不再使用后会自动被清空，时间一般为**几个小时到几天**
>
> — kv_cache 页"其它说明"，2026-09-08 抓取

三个后果，协议全都要用：

1. **"不保证 100%"是文档级的天花板**。所以"≥95% 且逐轮都 ≥95%"这个门槛
   本身就依赖提供方配合；一次验收里出现一轮无法解释的 0%，正确结论是
   "重跑一次并记下两次的结果"，不是"C 的改动无效"。
2. **过期时间只有一个区间，没有下界保证**。协议因此不能写"间隔 X 小时以内"
   这种从文档推出来的数——文档没给下界。改成：**验收的 10 轮必须在
   30 分钟内连续完成**，并在报数时写明实际耗时。30 分钟不是文档里的数，
   是一个远小于"几个小时"的工程余量，选它的理由写在这里，以后有人想放宽
   就知道放宽的是余量而不是规范。
3. **构建耗时秒级** → 两轮之间不要抢跑。协议要求每轮之间至少间隔 5 秒。

### 1.5 隔离：按用户，可用 `user_id` 再分区

> 每个用户的缓存是独立的，逻辑上相互不可见，从底层确保用户数据的安全和隐私。
>
> — news0802 页，2026-09-08 抓取

> KVCache 隔离：`user_id` 用于我们对您业务侧用户进行 KVCache 隔离，以进行隐私管理
>
> — <https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit>，2026-09-08 抓取

**文档未说明**："用户"指账号还是 API Key（文档里唯一一句区分账号与 Key 的话
是"并发限制以账号粒度计，与 API Key 无关"，那句只管并发）。也**未说明**
两个不同模型能否共享同一条缓存。协议因此把 §4 的排除条件写成"换模型、
换 provider、换 Key 之后的第一轮都不纳入"——不是因为文档说会失效，
而是因为文档没说不会。

Iris 侧要注意：`serialiseRequest`（`fingerprint.ts:167`）把 `provider` 与
`model` 放进了被哈希的字符串**开头**，所以换模型会让 `prefixHash` 变化而
提示词一个字节都没动。这正是 §4.3 里那条歧义的来源。

### 1.6 口径与价格

> `prompt_tokens` … 该值等于 `prompt_cache_hit_tokens` + `prompt_cache_miss_tokens`
>
> — <https://api-docs.deepseek.com/zh-cn/api/create-chat-completion>，2026-09-08 抓取

Iris 的记录与这个口径对得上，且是**减过的**：
`mapUsage`（`translate.ts:104-115`）写 `inputTokens = prompt_tokens - cacheRead`，
所以 `billed = inputTokens + cacheReadTokens = prompt_tokens`，
而 `cacheReadTokens = prompt_cache_hit_tokens`。**本协议的百分比就是
提供方自己的 `prompt_cache_hit_tokens / prompt_tokens`**，没有二次换算。

价格（本 profile 的模型是 `deepseek-v4-flash`，settings.json 里就是这个值，
文档当前价格表也列它）：

| 每百万 token | 高峰 | 空闲 |
|---|---|---|
| 输入·缓存命中 | 0.10 元 | 0.05 元 |
| 输入·缓存未命中 | 3.0 元 | 1.5 元 |
| 输出 | 9.0 元 | 4.5 元 |

> 空闲时段价格为高峰时段价格的一半。高峰时段为北京时间周一至周五
> 9:00-12:00、14:00-18:00（其余为空闲时段）。
>
> — <https://api-docs.deepseek.com/zh-cn/quick_start/pricing>，2026-09-08 抓取

**命中价是未命中价的 1/30**，两个档位都是。所以从 19.6%（当前实测，
`CACHE-CENSUS.md` §3）提到 95% 意味着输入侧成本降到约 1/4.3——
这是"值得做"的量级，也是验收要守住的量级。

### 1.7 关于保活请求：文档既不允许也不禁止

站内对 `预热` / `warm` / `定时` / `periodic` 的搜索在所有缓存相关页面
**零命中**；rate_limit 页那个"请求保活机制"讲的是 HTTP 连接的 SSE keep-alive
（`: keep-alive` 注释行、"如果 10 分钟后，请求仍未开始推理，服务器将关闭连接"），
**与缓存无关，不能当成缓存保活的依据**。手动控缓存被明确拒绝：
Responses API 的 `prompt_cache_key` / `prompt_cache_retention` 是
"不支持。上下文缓存自动管理"，Anthropic 兼容端点的 `cache_control` 是 `Ignored`。

所以**保活方案（每 N 分钟重发一次前缀让缓存不过期）在文档上既无授权也无禁止**。
它会按普通请求计费、占一个并发额度、超限得 429。协议的立场：
**不把保活写进验收路径**，只在 §6 记为一条待裁决的选项，理由是它会让
"我们的装配稳定"与"我们花钱把缓存捂热"两件事在数字上无法区分。

## 2. 测什么数：提供方回报，不是上界

**验收只看提供方回报的数。上界是诊断工具，不是验收指标。**

理由是这一轮量出来的：上界与回报在同一轮上可以差 73 个百分点
（`CACHE-CENSUS.md` §3，爱衣第 22 条消息那轮：上界 73.7%，回报 0.0%），
而 §1.2 说明这个差距可以完全来自提供方一侧。一个只看上界的验收会在
"我们把装配修好了、命中率一点没涨"时通过。

上界的用途有两个，都写进 PR：

1. **上界 < 95% ⇒ 不必发请求就知道达不到**。这是 C 的快速回归：
   `node scripts/cache-cause-census.mjs`（不发网络）算出每条会话的上界，
   低于 95% 的会话直接说明还有内容落在分叉之后。
2. **回报远低于上界 ⇒ 去查 §4.3 的两条歧义**（我们抖了 vs 提供方没给），
   而不是继续改装配。

## 3. 在哪条会话上测：验收会话的建法

不用用户现成的会话。理由：现成的 16 条里只有 2 条有 ≥2 轮生成，
其中 `爱衣` 的世界书与卡在测量期间还在变（`CACHE-CENSUS.md` §4.2），
而验收需要一个**能重跑**的东西。

**验收会话 A（主）——真卡真书，最接近用户处境**

- 卡：`爱衣`（跑 MVU，有 depth 0 变量表，是用户抱怨的那条会话的卡）。
- 预设：用户当前的 `咩咩预设 - ver 5.8.1`，不改任何开关。
- 设置：`contextWindow` / `maxTokens` / `temperature` / `seed` /
  世界书 `budgetPercent` / `budgetCap` / `insertionStrategy`
  **在整段验收里一个都不动**（§1.1：文档没说采样参数不参与前缀）。
- 浏览器**开着**，卡脚本照跑。这一条不能省：headless 看不到
  `ChatEntry.extensionPrompts`，而 §5 的实测说明一条落在 `main` 旁边、
  每轮都变的注入能把上界压到 0.4%。验收必须覆盖这条路径。
- 从新建会话开始，用固定的 12 句用户发言（写死在验收脚本里，不即兴发挥），
  每句之间等 ≥5 秒（§1.4），全程 ≤30 分钟。
- 记录：每轮的 `prompt_tokens` / `prompt_cache_hit_tokens`、`promptHash`、
  `prefixHash`、`model`、`provider`、`at`（后四项自 `ecc0b3e` / `9f7bb46` 起
  已经会写进 `iris_usage`）。

**验收会话 B（对照）——把 §5 的 0% 形状装进来**

同 A，但在每轮生成前用 `script.setExtensionPrompt` 注册一条**每轮都变**的
`position: 'before'` 注入（内容形状照 `cache-cause-census.mjs` 的
`mvuShapedInjection`）。B 的预期结果是**逐轮 ≈0%**。

B 存在的理由是 `A passing gate can answer the wrong question`：只有 A 的话，
一个"什么都没修好但提供方今天心情好"的运行也会绿。B 是那个必须**红**的样本，
它红了才说明 A 的绿是 A 的装配换来的。**A 绿 + B 不红 = 验收无效，重跑。**

**验收会话 C（易变宏）**

卡 `OVERLORD不死者之王`。它的 `worldInfoBefore` 里有一块每次装配都重掷的
`{{roll}}` 骰池（`CACHE-CENSUS.md` §2），落在第 7 873 字节 / 约 2 330 token 处。
C 的预期是**在卡作者不改条目的前提下上界锁在 9.6%**，任何声称"修好了 C"的
改动都必须说清它改的是卡的语义还是我们的装配。

## 4. 哪些轮不算：纳入与排除

### 4.1 排除清单

| 排除 | 理由 | 出处 |
|---|---|---|
| 每条会话的**第 1 与第 2** 个生成 | 文档明写"前两次请求不会命中缓存"；第二轮只负责把公共前缀落盘 | §1.2 |
| 换卡后的第一轮 | 提示词头部整体换掉 | — |
| 改设置（预设、世界书选择、预算、`contextWindow`、`maxTokens`、采样）后的第一轮 | 文档没说这些不参与前缀 | §1.1 |
| 换模型 / 换 provider / 换 Key 后的第一轮 | 文档没说跨模型能共享缓存 | §1.5 |
| 距上一轮超过 30 分钟的那一轮 | 缓存"几小时到几天"过期，但**没有下界保证** | §1.4 |
| 自动 compaction 触发的那一轮 | 摘要替掉旧历史，前缀在摘要处断开；`DEFAULT_THRESHOLD_RATIO = 0.8`（`compaction.ts:93`） | 见 4.4 |
| 卡脚本自己发起的生成（`script.generate` / `script.generateRaw`） | **它们根本不进 `iris_usage`**，见 4.5 | — |
| swipe（同一条消息的重掷） | 与相邻轮不是同一个总体，见 4.6 | — |

### 4.2 一条不能违反的规则：上界与回报必须来自同一个请求

上一轮把六个真实轮次的回报与九对相邻轮的上界并排，得出"差距 43–75 pp"。
**这一列不成立**，原因是本轮量出来的：同一条 `爱衣`、同样是"14 条消息那一轮"，
2026-09-01 真实发出去的请求是 10 734 token，而 2026-09-08 用今天的世界书
和今天的卡重装同一段历史是 **23 803 token**——两倍多。语料在两次测量之间长大了
（depth 0 那块从 5 367 字节长到 16 498 字节）。

所以：**验收里的上界必须和回报同一轮、同一天、同一份世界书**。
`cache-cause-census.mjs` 的"real pairs"walk 是回溯历史重装的，它给的是
"今天重装那段历史"的上界，**不是当初的上界**。验收要用的是 A 会话跑完之后
立刻算的上界。

### 4.3 回报为 0 时，先分清是哪一侧

`fingerprint.ts` 就是为这个建的：两轮 `prefixHash` 相同而 `cacheReadTokens`
为 0 指向提供方；不同则指向我们。**但这条判据现在有两个已知的坑，PR 报数时要一起报**：

1. **`prefixHash` 的窗口里含路由**。`serialiseRequest` 把 `provider` 与 `model`
   写在字符串开头（`fingerprint.ts:167-176`），所以换一次模型就让
   `prefixHash` 变化，而提示词没动。本轮语料里就有一个只能这样解释的样本：
   爱衣第 26 条消息的 swipe 2 回报命中 7 424 token，而它的 `prefixHash`
   与 swipe 1 不同——4 096 字节在这份语料里约 1 138 token（110 562 B / 30 696 tok
   = 3.60 B/token），若提示词真的在前 4 096 字节内变了，命中就不可能超过约
   1 138 token。两个前提有一个是错的，而路由变化是唯一与两个观测都相容的解释。
   **验收时 `model` / `provider` 已经会被单独记下（`9f7bb46`），
   所以报数时把它们和 `prefixHash` 一起贴，先把路由排除掉再谈归因。**
2. **`prefixHash` 只覆盖前 4 096 字节**（`PREFIX_BYTES`，约 1 138 token）。
   两轮 `prefixHash` 相同只证明前约 1 138 token 一样，**不证明**第 1 200 个
   token 一样。所以"`prefixHash` 相同 + 0% 命中"是**指向**提供方，
   不是证明——除非同时 `promptHash` 也相同（那才是整个 body 一样）。

### 4.4 compaction：一条必须单独报的结构性原因

自动 compaction 在可用预算的 80% 触发（`compaction.ts:93`
`DEFAULT_THRESHOLD_RATIO = 0.8`），把较早的历史换成模型写的摘要，只保留 16%
逐字原文（`DEFAULT_RETAIN_RATIO = 0.16`）。摘要坐在历史的**开头**，
所以它一出现，前缀就在那里断开，而且它每次重新总结都会再断一次。

本 profile 现在还没有任何一条会话有 `iris_compaction` 记录
（`grep -l iris_compaction chats/*.jsonl` 无输出），所以本轮没有实测样本。
**协议要求 PR 明确写一句"本次验收期间 compaction 未触发"，
并附 `grep -c iris_compaction` 的输出**：这条排除项如果只写在文档里而没人查，
它就是一个随时会安静地推翻整段验收的原因。

**阈值的算法这一轮改了，数字要按新的算**（`DEVIATIONS.md` §56）。
分母是 `context − reserve`，而 reserve 现在取 `settings.maxTokens`
（照上游 `openai.js:1558`→`:3887` 的 `max_context − max_tokens`），
不再是宿主常量 1 024。用产品自己的读数在 `爱衣` 上量过（`chat.open` 的
`ChatBudget` 与 `prompt.itemize`，只读拷贝，未发请求，2026-09-09）：

| | 改之前（reserve 1 024） | 改之后（reserve 65 535） |
| --- | --- | --- |
| context（受 §44 模型钳制，存的是 2 000 000） | 1 000 000 | 1 000 000 |
| available | 998 976 | 934 465 |
| 80% 阈值 | 799 180 | **747 572** |
| 16% 保留尾 | 159 836 | 149 514 |
| `爱衣` 下一条请求 | 22 546 tok（2.8%） | 22 546 tok（3.0%） |

所以阈值低了 6.5%，方向正确（上游同样是这个分母），
但 `爱衣` 离两个阈值都还有 33 倍，短期内仍不会触发。

**而且：compaction 的摘要请求现在会进用量与命中率的分母。**
见下面 §4.5 末尾——它带 `source: 'compaction'`，
所以 PR 报数时它是**单独一列**，不能混进 (a) 或 (b)。

### 4.5 不是回合的那些请求：曾经在总体之外，现在进了总体

**这一节写的是原来的缺陷与它的现状，不是一条待办。**
原来：`script.generate` → `#sideGenerate` → `this.#stream({...})` **不传
`entry`**，而 `noteUsage` / `notePromptFingerprint` / `noteRoute` 都挂在
`entry?.pending?.turn` 上，所以卡脚本发起的生成不写 `iris_usage`、
不写 fingerprint、不进用量页，也不进对话自己的累计计费。

对 MVU 这类卡这不是边角情况：它每轮都会为"变量更新"再发一次请求
（`invoke_extra_model.ts:511`，带 `<past_observe>` 注入）。也就是说
在这类卡上，没被记账的那一群和被记账的那一群**一样大**。

现在（`DEVIATIONS.md` §51）：这些请求各写一条只追加的记录，
落在对话头的 `iris_side_usage` 上——它不属于任何一楼的 swipe，
所以不能进消息的 `iris_usage` 数组（那个数组与 `swipes` 平行）。
每条带桶、路由、时刻、fingerprint、`source: 'script'` 与 `caller`
（RPC 方法名；契约里没有脚本 id 可记，`script.generate` 只带
`chatId`/`userInput`/`systemPrompt`/`maxHistory`）。
`ChatView.usage` 与 `usage.summary` 的每个数字都已把它们算在内，
并用 `ChatView.scriptUsage` / `UsageTotals.script` 单独报出这一份。

**同一个数组现在装两群人**（`DEVIATIONS.md` §55），所以
"位置就是权威"这条规则拆成了两半：**位置**判定"这不是一个回合"
（数组里写 `source: 'turn'` 仍然被拒），**存下来的字段**在两种 side source
之间选。读不出 side source 的记录按 `'script'` 计——这不是猜，
而是那一群人：`'compaction'` 在 §55 之前不存在，
所以此前写进这个 key 的每一条都是卡的。

**协议因此要求 PR 写清四个数**：
(a) 用户可见回次（消息行上的 `iris_usage`）的命中率；
(b) 卡脚本请求（对话头上 `iris_side_usage` 里 `source: 'script'` 的那些）
的命中率，**单独一列**；
(c) compaction 摘要请求（同一个数组里 `source: 'compaction'` 的那些）的命中率，
**也单独一列**；
(d) 三者合起来的命中率，也就是最接近账单的那个数。
四条都要，因为 (d) 是用户付的钱，而前三条的分母上界互不相同：
`script.generate` 会把整段前缀重发一遍，`script.generateRaw` 只发卡递给它的
那点东西，`#summarize` 重发的是**被折叠掉的那一段**——混在一个分母里会把三种
现象平均掉，和 §4.6 对 swipe 的理由相同。

**原来在总体之外的那一项，现在进了总体**（`DEVIATIONS.md` §55）：
compaction 的摘要请求（`#summarize`）同样被计费、同样不产生候选，
过去既不传 `entry` 也不传 trace，所以不进任何数字——一个压缩过的 profile
每次 compaction 少算一条，页面上也没有任何数字说少了什么。
现在它走 `#stream(..., { entry, caller: 'host.compaction', source: 'compaction' })`，
和卡脚本的记录落在**同一个** `iris_side_usage` 数组里，
并另留一条 `kind: 'compaction'`、`turn: -1` 的 trace
（摘要坐在下一条请求历史的最前面，所以它是唯一能解释"之后每一轮前缀为什么都变了"
的那份请求体）。`UsageTotals.compaction` 与 `ChatView.compactionUsage`
是它自己那一份，和 `script` 并列而不合并：卡的花费是卡作者的决定，
compaction 的是 Iris 自己的策略，读者要少花哪一种，动的地方不一样。

§4.4 仍然要求 PR 附 `grep -c iris_compaction` 的输出：那个数是 0 时
(c) 这一列是空的，而这正是那条排除项要被人真去查的原因——
一旦它不是 0，(c) 就有值，而它的分母是被折叠的那一段，永远不该被平均进 (a)。

**一条前提纠正**：普查把 MVU 那个"35 字符随机 uuid 头"记成了 gemini 路径的
问题（`CACHE-CENSUS.md` §7.1 与本文件旧版本）。它是**卡自己的代码**：
`invoke_extra_model.ts:44` 造出这个块、`:570` 把它作为 `role: 'system'`
提示词拼在最前面，条件是卡自己的 `随机头部` 设置**且**模型名含 `gemini`。
它经 `prompt` 传进来，Iris 侧没有任何东西可删——本仓请求装配路径里没有
`randomUUID`。上游 SillyTavern 确实也加一个 uuid，但机制不同、不在被缓存的
前缀里：`bodyParams['user'] = uuidv4()`
（`src/endpoints/backends/chat-completions.js:2212`），只在 OpenAI 源上，
受 `openai.randomizeUserId` 配置控制，默认关。
Iris 现在能做的是**把它报出来**：这条请求连同 `prefixHash` 一起存下来，
所以"卡自己的头把自己的缓存打掉了"会表现为一条 `script.generate` 记录的
prefix 哈希每次都变，而同一对话的回次哈希没变。

### 4.6 swipe 单独报

同一条消息的多次 swipe 历史相同，但本轮语料里它们的 `prompt_tokens` 是
12 343 / 12 343 / 15 594 / 20 935（爱衣第 26 条消息），一路在长，
而磁盘上的 `stat_data` 只有 745 字节且这条消息上根本没有变量层
（`CACHE-CENSUS.md` §4.3）。也就是说 swipe 之间有东西在长，而它不在磁盘上。
在弄清那是什么之前，swipe 与相邻轮混在一个分母里会把两种现象平均掉。
**swipe 单独一张表。**

## 5. 每个原因修好之后，上界预期到多少

全部实测，来源 `CACHE-CENSUS.md`，都是"不发网络"的上界，
所以它们是**必要条件**（上界不到 95%，回报不可能到 95%），不是充分条件。

| 原因 | 现在的上界 | 修法 | 修后上界 | 谁能修 |
|---|---|---|---|---|
| 每轮变的注入落在 `main` 旁（`position: 'before'`） | **0.6%** 均值（16 张卡，0.2%–1.2%） | 同一条注入改成 `at-depth 0` | **41.0%** 均值，即回到无注入基线 41.1% | 卡作者；Iris 侧只能提示 |
| 每轮变的注入落在 `main` 之后（`'after'`） | **3.9%** 均值（1.4%–8.0%） | 同上 | 同上 | 同上 |
| `worldInfoBefore` 里的 `{{roll}}` 骰池 | **9.6%**（OVERLORD ×3）、22.7%（创世回廊） | 把骰池条目从 position 0 改到 depth 0 | 同状态抖动完全消失（实测：删掉整段 wiBefore 后同状态上界 99.9%）；合成 +1 轮 **≥46.5% / ≥60.9%**（"删掉整段"的实测值，只搬骰池会更高） | 卡作者 |
| depth 锚定内容每轮逐字重发 | 爱衣 74.9%（10 对真实轮 67.2%–73.7%） | 把**逐字稳定**的部分放进稳定前缀 | **98.0%**（合成对）；真实轮里稳定的 6 对 **95.0%–98.6%** | 用户旋钮 / 卡作者 |
| 同上，但那块内容**自己每轮变** | 4 条会话 7.6%–55.2% | 搬上去 | **变得更差**：2.1% / 0.0% / 0.0% / 19.5% | — |
| 历史自然增长 | — | 无法消除 | — | — |

**这张表最重要的一行是倒数第二行**：同一个"搬到前缀里"的动作，
在 8 条会话上把上界推到 ≥96%，在 4 条会话上把它砸到 ≤19.5%，
区别只在那块内容**逐字节是否稳定**。所以：

> **C 的改动必须先判定稳定性，再决定搬不搬；不能对 depth 内容一律搬。**
> 判定要按"两个相邻轮的这块内容是否逐字节相同"来做，不能按"它看起来像不像模板"。

关于"一轮新增多少"的算术，仍然是门槛能否达成的前提，只是结论变了：
爱衣一轮新增约 2 157 字节（占 110 562 字节的 **2.0%**），
所以理论上界是 98%——而实测把 depth 内容放进前缀之后正好是 **98.0%**，两者吻合。
**如果 C 报出一个 ≥95% 的上界，要核对的是它仍然在同一个"一轮新增两条消息"
的形状下测的**——把新增放小、把总长撑大都能把这个比例做漂亮。

## 6. 待裁决（不在本协议内）

1. **保活请求**（§1.7）。会让"装配稳定"与"花钱捂热"在数字上无法区分；
   若要做，必须先给它一个开关，并在验收里跑关掉它的对照。
2. **`prefixHash` 的窗口里含路由**（§4.3）。修法很小（把 `provider`/`model`
   移出被哈希的字符串，或再记一个不含路由的哈希），但它改的是已经落盘的
   记录格式，且 `model`/`provider` 现在已单独记下，所以也可以选择"不改代码、
   在分析时减掉"。这一条影响 A 的分叉归因仪器，需要总指挥先定。
3. **一个记录到 `script.generate` 用量的口子**（§4.5）。不改会让"全 profile
   命中率"永远窄于账单。改动很小（把 `entry` 传进 `#stream`），
   但会把卡脚本的请求混进用户可见的用量图，需要先定产品语义。

## 8. 本协议自己的弱点

写下来，因为下一个人会拿它当规范用：

- **样本只有一条真实长会话**。爱衣是这份语料里唯一有 ≥2 轮生成且历史够长的
  会话（`CACHE-CENSUS.md` §1），所以 §3 的验收会话 A 是**新建**的，
  它不能证明"用户现有的会话也会好"。
- **30 分钟窗口是工程余量，不是文档规范**（§1.4）。文档只给了"几小时到几天"
  的上界侧描述，没给下界。
- **"逐轮 ≥95%"依赖提供方配合**，而文档明写不保证 100% 命中（§1.4）。
  一次红不一定是回归；两次红才是。协议要求重跑一次，并把两次都贴出来。
- **上界的 token 是估算的**（`@iris/tokenizer`，本语料 3.60 B/token），
  提供方的分词器我们拿不到。所以上界的百分比有几个点的不确定度，
  而回报的百分比没有——这也是 §2 只用回报做验收的第二个理由。
